设计原则：所有入口都汇入同一个「阅读库收件箱」（文章 + 随记混排，类型徽章区分）；所有路由都用 virgo:// 深链回主界面，通知按钮和小组件按钮不新增任何原生界面；同步只有一条路径（全量对账，幂等），手动点击与自动触发共用。

2. 数据模型：统一收件箱 阅读库扩 kind 字段，随记是「一等的文章」

articles 表（SQLite WAL，阅读库现有表）
  kind        TEXT  DEFAULT 'article'   -- 'article' | 'note'（新增，旧行默认 article）
  id          TEXT  PK
  url         TEXT  UNIQUE              -- 唯一键复用，见下方三种取值
  title / site_name / excerpt / byline / cover_file
  content_html TEXT                     -- 渲染结果（随记保存时由 markdown 重算）
  markdown    TEXT                      -- 随记的事实源（文章则为导出的 md）
  word_count / reading_minutes / added_at / progress_percent / read_at
  annotations / context / links…（原样不动）
  updated_at  INTEGER  -- 新增：note 用它做 LWW 冲突裁决；article 同步不动它

url 唯一键的三种取值（去重即复用现有 find_by_url）

条目类型url 取值去重行为
网络文章真实 URL（现状）同一链接重复添加 → 回跳已有文章（现状）
本地文件文章local-file://<sha256 前 16 位>同一文件（内容相同）重复打开 → Toast「已在收件箱」并直达
随记note://<id>无去重需求，id 天然唯一

随记（note）的行为定义

  • 事实源是 markdown 字段：编辑器直接改源码，保存时 pulldown-cmark 重算 content_html、title（首个标题行或首行截断）、excerpt、word_count。
  • 无进度语义：随记卡片不显示阅读进度条；read_at 用作「已阅」归档标记（可选）。
  • 可分拣：桌面端分拣（capture → task）改为从收件箱取 kind='note' 条目，分拣完成后条目标记 triaged（context 字段记目标列），与现有 CaptureView 工作流对齐。
  • inbox.md 退役：桌面随记事实源从 ~/.todo/inbox.md 迁入阅读库（一次性迁移命令 todo capture migrate，原文件改名 inbox.md.migrated-2026xxxx 留档）；CLI 不读 inbox.md（已核实），无连带影响。
决策 · 决策③ 的更新

原决策③「移动端没有本地事实源」按阅读库例外口径修订：阅读/收件箱是本地 SQLite + 服务器对账的副本库（与文章现行做法一致），任务事实源仍只在受管 TODO.md。正式立项时更新 DECISIONS.md。

规则

  • 编辑即改 markdown 字段，保存时重算渲染字段并 bump updated_at；标题输入框只改 title，不回写正文。

6. 文件关联：文件管理器「打开方式」 VIEW intent + content:// 接收链

6.1 注册（AndroidManifest.xml，声明式 ~10 行）

<!-- MainActivity（singleTask，已是现状）加第二个 intent-filter -->
<intent-filter>
  <action android:name="android.intent.action.VIEW" />
  <category android:name="android.intent.category.DEFAULT" />
  <data android:mimeType="text/html" />
  <data android:mimeType="text/markdown" />
  <data android:mimeType="text/x-markdown" />
  <data android:mimeType="text/plain" />  <!-- 按需求收入；靠嗅探分流 -->
</intent-filter>
已知代价（已接受）

text/plain 会让 .txt / .log / .csv 等所有纯文本的「打开方式」都出现 Virgo——用内容嗅探分流化解（见决策树），并在设置里提供「收件箱 · 忽略 text/plain」开关一键退订。

部分文件管理器把 .md 报成 application/octet-stream，这类会漏网（收 octet-stream 会污染所有二进制文件，不做）；已知限制，真机验收时记录各主流管理器表现。

6.2 接收链路（官方 Mobile Plugin 开发路径，全仓唯一自研平台触点）

文件管理器点开 xx.md
  → MainActivity.onCreate / onNewIntent（singleTask）      -- 现有类，加 ~6 行转发
  → InboxPlugin.onIntent(intent)                         -- 自研最小 Tauri Android 插件（Kotlin）
      ├─ ContentResolver.openInputStream(content://) 读字节（≤ 10MB 上限 = MAX_PAGE_BYTES）
      ├─ 写 cacheDir/incoming/<ts>-<安全文件名> + 顺手记 MIME / 原始文件名
      └─ emit inbox://incoming 事件（热启动实时通知）
  → 前端收事件 → invoke inbox_import_incoming()（Rust 扫描 incoming/ 目录）
      ├─ 逐文件：sha256 → 伪 URL → 去重检查 find_by_url（命中 → Toast「已在收件箱」直达）
      └─ 未命中 → 嗅探分流（§6.3 决策树）→ 入库 → 清理 incoming/ 文件
  → 冷启动兜底：前端启动时固定 invoke 一次 inbox_import_incoming()（事件只是加速，不依赖它）
为什么 content:// 不走 tauri-plugin-deep-link

官方 deep-link 插件面向 URI scheme；对 content:// 这类非 URL 数据不保证触发 onOpenUrl（社区 issue 佐证）。所以分工：URI 路由（通知/小组件按钮）走官方 deep-link 插件，content:// 文件走自研插件——后者同时承载常驻通知与小组件，三件事一个插件解决（≤300 行 Kotlin + Rust 薄壳）。

6.3 嗅探决策树（Rust 侧 inbox_import_incoming）

读入字节 → UTF-8 解码（失败 → 转随记附件式收录，正文按纯文本）
├─ MIME=text/html 或 内容匹配 <!doctype html|<html[ ]
│    → HTML 文章：走 add_fetched 现成管线（readability 提取 + 图片本地化），url = local-file://<sha>
├─ 扩展名 .md/.markdown 或 特征（首行 # / - [ ] / ```）
│    → MD 双问动作条（§6.4）：加入阅读 / 导入为 TODO / 仅预览
└─ 其余 text/plain → 默认按随记收（直接进编辑抽屉，可改名 / 丢弃，不骚扰）

9. 一端同步，全端加载 协议 v3 + 触发矩阵 + 状态条

9.1 现状（直接复用）

  • 全量对账以 URL 为唯一键：本地上行只传 URL+上下文（服务器解析），下行拉服务器已解析正文与图片（GET /articles/{id}），幂等、可重入（SYNC_LOCK 单实例闸门）。
  • SSE 自动同步已有：GET /stream 变更事件 → 对账，断线 5s→60s 退避；桌面端已跑通，移动端同代码直接启用（前台在线时 ≤1s 收到别端变更）。
  • 手动同步按钮、启动对账、进度事件（reading://sync-progress）均为现状。

9.2 协议扩展（v3，服务器宽容兼容）

POST /links  body 扩展（新字段全部可选，旧客户端不受影响）：
  { url, context?,
    kind?,            -- 'article'（默认）| 'note'
    title?, markdown?, content_html? }
  ├─ 无 content 字段 → 服务器抓取解析（现状，网络文章）
  ├─ 带 content（local-file://… / note://…）→ 服务器原样入库不解析（本地文件/随记的正文只在客户端）
GET /articles、GET /articles/{id} 返回体补 kind / markdown / title
/stream 不变：note 变更同样发 change 事件

9.3 冲突策略（分层）

数据策略说明
文章备注 / 进度互不覆盖（v1 现状）创建时随行，之后各端独立
随记正文（note）updated_at LWW（整篇）小文本整篇覆盖可接受；编辑抽屉显示「最后编辑 x 前 · 来自 哪端」，被覆盖端下次对账时提示一次可回滚（服务器保留上一版 7 天）
本地文件文章正文只增不改正文来自文件导入，各端不会编辑它，无冲突面

9.4 触发矩阵（点击同步 + 自动同步都要）

时机行为实现
App 启动 / 回到前台全量对账（离线期间积累的上行 + 拉取别端变更）现状 reading_resume_pending + 启动对账
顶栏「⟳ 同步」按钮 / 通知 action / 小组件手动全量对账 + 状态条反馈现状 reading_sync_now，入口变多而已

Android 后台不保活、不后台同步系统杀进程即停；下次打开启动对账兜底（移动端合理取舍）
