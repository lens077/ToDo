# 首次运行引导规格

本文定义 CLI 与桌面端的首次运行体验。范围是「从零到第一次感受到对账引擎的价值」，不包含账号、登录与付费流程。

设计语言、配色与字体沿用 `docs/desktop-mvp-spec.md` §2，本文不重复定义。

## 0. 目标与反目标

**唯一北极星指标：time-to-first-value（TTFV）。**
`research/b-markdown-local-first-tools.md` 记录的 imdone 十二年教训把这一条定为生死线；`DECISIONS.md:13` 同样把 TTFV 列为选择单文件 TODO.md 的首要理由。引导的每一步都要为它让路。

**三个反目标（明确不做）：**

1. **不做多步向导。** 开发者装工具是为了立刻用，不是填表。任何「第 2 步，共 5 步」的进度条都是失败设计。
2. **不做功能巡览（feature tour）。** 不用蒙层箭头逐个指认按钮。价值靠真实数据呈现，不靠解说。
3. **不在引导期写任何用户没要求的文件。** 这是产品的信任地基（`README.md` 设计约束：工具只修改自己认识的行）。引导阶段尤其不能破例。

## 1. 首次运行的真实起点

引导不是一个新界面，而是**已经存在的三个入口**的补完：

| 入口 | 现状 | 现有实现 |
|---|---|---|
| `todo init` | 已实装，原子创建，遇已存在文件拒绝写入 | `crates/todo-cli/src/main.rs:783` |
| 桌面端 `no-project` 空状态 | 已实装「选择一份真实的 TODO.md」 | `apps/desktop/src/components/EmptyState.tsx` |
| `todo hooks install` | 已实装，支持 claude / codex / deepseek-harness | `crates/todo-cli/src/hooks.rs` |

**结论：不新建向导框架，只在这三处补引导。** 这也让引导天然可跳过——老用户什么都不会多看到。

## 2. CLI 首次运行

### 2.1 `todo init` 之后的下一步提示

现状：`init` 成功后只打印 `initialized TODO.md`，用户不知道下一步做什么。

改为在人类可读输出（`--json` 时不变，保持 envelope 稳定）后追加：

```text
initialized TODO.md

下一步：
  todo add "第一个任务"     记一件事
  todo scan                 扫描仓库里已经存在的 TODO 注释与 checkbox
  todo hooks install        让 agent 每次会话自动读到任务清单
```

`todo scan` 放在第二位是刻意的：**它是本产品最快的「哇」时刻**。新用户在一个真实仓库里跑 `todo scan`，会立刻看到几十条自己早就写下、却从没跟踪过的 `TODO` / `FIXME`。这比任何示例任务都有说服力，且完全不写盘（`--import` 才生成提案，`--yes` 才回写）。

### 2.2 `todo init --adopt` 的引导价值

已有 GFM 清单的用户应当被直接引导到 `--adopt`。当 `init` 因文件已存在而失败时，错误信息里给出可直接复制的命令：

```text
error: TODO.md 已存在
提示：用 `todo init --adopt` 接管现有清单并补齐稳定 ID（会先建还原点）
```

### 2.3 空 TODO.md 上的 `todo list`

首次 `list` 面对空文件时，不打印空表，而是打印同一段「下一步」提示。**用户在哪里迷路，就在哪里给路标。**

## 3. 桌面端首次运行

### 3.1 复用现有的 `no-project` 空状态

`EmptyState.tsx` 已有正确的骨架与文案基调（`LOCAL FIRST / NO PROJECT` + 「桌面端不会自动接管」）。只做两处增补：

1. **第二个动作按钮**：除「选择项目」外，增加次级动作 `line-action`「还没有 TODO.md？」，点击展开一段说明，指向在已有仓库里跑 `todo init` 或 `todo scan`，而不是由 GUI 悄悄创建文件。
2. **保持不自动接管的承诺**：选择的目录若无 `TODO.md`，**不静默 init**，而是显式询问，并说明将创建哪个文件。

### 3.2 首个项目载入后的「第一屏」

用户第一次成功载入项目时，今日视图很可能是空的（任务都没有截止日期）。此时的空态不应只说「今天没有任务」。

- 若项目有任务但今日为空 → 引导至看板，并提示「给任务加上截止日期，它们会出现在这里」。
- 若项目**完全没有任务** → 显示单一主行动：**「扫描这个仓库」**，直接调起 `scan` 视图。

这再次把新用户推向 `scan`——首屏就展示「你的仓库里其实有 37 件没跟踪的事」，是本产品最强的首次价值证明。

### 3.3 对账引擎的首次揭示（最关键的一步）

对账引擎是付费理由（见 `docs/business-model-options.md`），但它**只有在有 Git 物证之后才有话可说**。因此不在首次运行时推销它，而是**等它第一次真正有输出时才出现**。

触发条件（全部满足）：

- 用户已完成过至少一个任务；且
- 该项目是 git 仓库，`reconcile` 返回了至少一条 finding。

首次出现时，在 `StatusBanner` 展示一次性说明：

> **对账发现 2 处不一致。** 它用 Git 物证核对任务与代码的实际状态，**只报告，不改写你的完成状态**。

这条说明只出现一次。**「只报告，不改写」必须在第一次就说清**——`research/c-commercial-mainstream.md` 的叙事建议第 2 条（「AI 提议，你确认」，对照 Height 全自动失败与 Microsoft 回撤 draft 模式）正是本产品的信任支点。

### 3.4 BYOK 的延迟询问

语义对账需要 `TODO_LLM_API_KEY`（`crates/todo-core/src/llm.rs`）。

**绝不在首次运行时索要 API key。** 开机就要密钥是最高效的劝退方式，而结构化对账（不需要密钥）本身已经有价值。

正确时机：用户主动进入 `ProviderSettings`，或**结构化对账已经跑通、且出现了只有语义层能判断的情况**时，才提示可选配置，并说明这是 BYOK——**用你自己的 API key，请求不经过我们的服务器**。这句话本身就是信任资产，要说出来。

## 4. Agent 接入引导

`todo hooks install` 是本产品与竞品拉开距离的地方，但新用户不会自己发现它。

- `init` 的下一步提示里列出（见 §2.1）。
- 桌面端在**用户已完成 3 个以上任务**后，于命令栏一次性提示：「让 agent 自动读到这份清单？」→ 展示 `todo hooks install --agent <检测到的 agent>`。
- 检测依据：本机是否存在 `~/.claude/settings.json`、`AGENTS.md` 等目标文件，`hooks.rs` 的 `plan()` 已有这套路径逻辑，直接复用。
- ⚠️ 引导中**不得**执行 `todo hooks preview` 的输出展示到任何非本地界面：README 已警告该输出可能包含 API 密钥。

## 5. 全局规则

1. **一切引导可跳过，且只出现一次。** 状态记在 `~/.todo/` 下的本地配置，**不写进用户仓库**（同 Capture 的处理，见 `docs/adr/0001`）。
2. **引导不写用户仓库的任何文件。** 唯一例外是用户显式确认的 `init` / `scan --import --yes`。
3. **不做遮罩层教学。** 提示以行内说明、空状态和 `StatusBanner` 呈现。
4. **动效遵守既有约束**（`desktop-mvp-spec.md` §2）：只表达状态变化，禁止持续浮动与弹跳。
5. **文案不用感叹号，不用「欢迎使用！」。** 目标用户是开发者，克制的说明比热情的招呼更可信（参见 `tech-doc-style-chinese` 的风格约定）。

## 6. 验收标准

- [ ] 全新用户在真实仓库中，从 `cargo install` 到看见第一批扫描结果，**命令数 ≤ 3**（`init` → `scan`，或直接 `scan`）。
- [ ] 桌面端从空状态到载入项目，**点击数 ≤ 2**。
- [ ] 引导全程**零非预期写盘**：跑完首次流程后 `git status` 除用户显式确认的改动外干净。
- [ ] 首次运行**不索要 API key**，且不配置 key 时结构化对账完全可用。
- [ ] 所有一次性提示在第二次运行时不再出现。
- [ ] 老用户（已有配置）升级后，**看不到任何新增引导界面**。
