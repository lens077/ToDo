# 标题优先级推断规格

> 前置约定：`CONTEXT.md`、`docs/format-spec-v1.md`（`!1`..`!4`，1 最高）、`docs/priority-quadrant-spec.md`。
> 实现：`crates/todo-core/src/heading_priority.rs`；回归：`crates/todo-core/tests/heading_priority.rs`。

## 1. 用途与边界

手写任务文件常用标题分组表达优先级，而不给每一行加 `!n`。例如 ecommerce 的 `TODO.md` 在领域三级标题下放 `#### P0` / `#### P1` / `#### P2`，也有 `#### P1 · 线 B：领域事件` 这类带副标题的写法。

本算法把这种结构读成**派生优先级**：

- 只读，不写文件。不会自动插入 `!n` token，也不会改写原有标题。
- 任务行上的 `!n` 永远优先于标题推断。
- 输出始终归一到原生四档 `!1`..`!4`。原始标签（如 `P0`）、来源标题和行号随结果一起返回，界面可以如实展示「来自哪个标题」。

## 2. 算法

分三步，彼此独立。

### 2.1 标签识别 `parse_priority_label`

输入一条标题的纯文本（已去掉 `#`、强调和行内代码的标记），判断其中是否带有优先级标签。

1. **归一化**：全角 ASCII 转半角（`Ｐ０`→`P0`，`：`→`:`，`（`→`(`）。
2. **去前缀装饰**：去掉开头的 emoji、符号和编号（`1.`、`1.2`、`三、`、`(一)`）。
3. **头部匹配**（优先）：
   - 开头是括号 `[P0]`、`【P1】`、`(P2)` 时，括号内整体必须是标签；
   - `P<1–2 位数字>` 后可跟 `级`，其后须是边界：结尾、空格、标点或中文字符。字母、数字、`_` 和 `.数字` 都不算边界，因此 `P2P`、`P1.5` 不会被识别；
   - 否则取到第一个分隔符（`:` `·` `|` `/` `,` `;` `—` `–` `(` `[`、两侧有空格的 ` - `）为止的片段，整个片段必须是标签。若该片段只是关键词（`Priority: Low`、`优先级：高`），则取到下一段。
4. **尾部匹配**（头部未命中时）：
   - 结尾括号：`库存正确性 (P0)`；
   - 最后一个分隔符之后：`鉴权 — P1`、`鉴权：高优先级`；
   - 最后一个空格之后：`鉴权 P1`。

**独特性约束**：裸词（`High`、`紧急`）只在标题头部或括号内算标签。其余位置要求标签「独特」，即 `P` 编号、`!n`，或带有 `priority` / `优先级` / `优` 关键词。原因是 `Availability: High` 在描述属性，并不表示排序。

标签语法（大小写不敏感）：

| 族 | 示例 | rank |
|---|---|---|
| `PNumber` | `P0` `p1` `P0级` `Priority 1` `优先级 2` `优先级：P0` | 编号本身 |
| `Word` 强词（可单独出现） | `Critical` `Urgent` `Blocker` `Highest` `紧急` `特急` `最高` / `High` / `Medium` / `Low` `Lowest` `最低` | 0 / 1 / 2 / 3 |
| `Word` 弱词（须带关键词） | `致命` / `高` / `中` `普通` `一般` `Normal` / `低` `Minor` | 0 / 1 / 2 / 3 |
| `Native` | `!1`..`!4` | 即档位 |

弱词单独出现太常见（`高级功能`、`中文文档`、`Normal form`），所以必须写成 `高优先级`、`低优`、`优先级：中` 等形式。

### 2.2 刻度归一

| 族 | 映射到 `!n` |
|---|---|
| `Native` | 原值 |
| `Word` | tier + 1：紧急→`!1`，高→`!2`，中→`!3`，低→`!4`，与象限四格名称一一对应 |
| `PNumber` | `n − origin + 1`，超过 4 折叠为 `!4` 并标记 `clamped` |

`origin` 按文档判定为 0 或 1：只要正文（不含行内代码与代码块）或任一标题标签中出现独立的 `P0`，就以 P0 为最高，否则以 P1 为最高。

说明段中的 `P0` 也计入判定，这是有意为之。ecommerce 的「一、优先级」说明段写着 `**P0：正确性与安全阻断**`；即使日后所有 P0 任务都已删除，剩下的 `P1` 仍应是 `!2`，不能因为 P0 分节消失而被静默提升到最高档。

### 2.3 章节作用域

按文档顺序维护标题栈：遇到 N 级标题时，先弹出所有级别 ≥ N 的标题，再压入它自己。任务取栈中**最近一个带标签**的标题。

- `### 微服务` → `#### P0` → 任务：`!1`。
- `#### P1` 之后出现 `### 数据一致性`：P1 的作用域到此结束，其后未进入新 `P` 小节的任务无推断值。
- `## P0` → `### 库存`（无标签）→ 任务：继承 `!1`；`### P2 延后` 下的任务：`!3`，就近者胜。
- 子任务按其所在位置推断，与父任务在同一小节时结果相同。
- frontmatter 不参与 Markdown 解析，因为它的结束行 `---` 会把最后一行 YAML 变成 setext 标题。代码块内的标题既不是标题，也不产生任务。

### 2.4 最终优先级 `effective_priorities`

`!n`（同一行重复时取最后一个，与桌面快照一致）＞ 标题推断 ＞ 无。返回值附带 `source`：`explicit`，或 `heading`（含标签、标题原文与行号）。

## 3. 验证

- 单元与集成用例 10 项，覆盖正例、反例（`一、优先级`、`Postgres`、`P2P`、`High availability`、`高级功能`、`Phase 1`、`Priority queue`……）、零基与一基刻度、折叠、说明段与行内代码、嵌套标题和 frontmatter。
- 以只读方式在真实的 `../ecommerce/TODO.md` 上运行：103 个任务中，98 个由 `P0`/`P1`/`P2` 标题（含 `P1 · 线 B` 等变体）推断，1 个保留行内 `!2`，4 个位于没有优先级小节的「文档与协作机制」下，结果为无。运行前后文件 SHA-256 不变。

## 4. 接入决定（2026-09-27）

核心算法已实现；以下是接入 CLI、`todo serve` 与桌面端时必须遵守的规则，尚未实现。

### 4.1 读标题不算「自动定级」

`PRODUCT.md` 与象限规格禁止的「自动定级」，指工具用截止日期、标签等其他信号替用户判断轻重。`#### P0` 是文件作者亲手写下的排序，读出来属于「界面按原样显示文件内容」。

因此推断值参与定级：象限按它归格，不计入「未定级」托盘；目标视图按它排序。否则 ecommerce 的 98 个任务会全部堆进未定级托盘，与文件事实不符。

### 4.2 展示：原标签 + 空心徽标

- 推断值显示**原标签**（`P0`），不显示换算后的档位名；空心描边徽标，与行内 `!n` 的实心徽标区分。
- 悬停／无障碍名称写明来源：「来自第 45 行标题「P0」」。
- 显示原标签是为了让用户一眼核对刻度换算：P0 是否被当作最高档，这一判断基于启发式规则（§2.2），必须可见。
- 行内 `!n` 与所在标题不一致时（例如 P0 小节里的 `!3`）只显示实心的 `!n`，悬停时补充一句「所在标题为 P0」，不告警。

### 4.3 改档与清除：禁止无效操作，而不是让它假装成功

| 操作 | 推断任务（无 `!n`） | 已有 `!n` 且所在标题带标签 |
|---|---|---|
| 拖到另一格／快捷键 `1`–`4` | 写入 `!n`，徽标变实心 | 改写 `!n` |
| 拖到当前推断格 | 无操作，不写文件 | 按原象限规则处理 |
| 拖到未定级／快捷键 `0` | **不可用**：放置目标显示禁止态，说明「优先级来自标题「P0」（第 45 行）。请在文件中移动任务或修改标题」 | 文案改为「**恢复为标题优先级 P0**」，删除 `!n` |
| CLI `todo priority <id> --clear` | 报错并给出同样的原因与标题行号，退出码非 0 | 删除 `!n`，输出提示回落到的标题优先级 |

否决的方案：

- **无操作并提示**：拖放会先落位、再弹回，违反「写入成功后界面才落位」的约定。
- **新增「无优先级」token**：改动格式规范，其他 Markdown 渲染器会显示这段杂讯；而且与象限规格 §8「不新增文件 token」冲突。

整组改档沿用象限规格：父卡决定归格，一次 subtree 写入。组内推断值与显式值混合时，沿用「组内原优先级不同」提示。

### 4.4 不提供批量写回

不提供「把标题优先级批量写成 `!n`」的操作，原因如下：

- 写回之后，标题和 token 成为两份事实。用户以后把任务从 P1 小节挪到 P0 小节时，残留的 `!2` 会静默覆盖新标题，文件越改越错。
- 真正需要显式值的任务，单个拖动就会写入，已经足够。
- 需求出现时再评估，而且只能按 Adoption 的方式执行：先预览差异，确认后写入，不能在后台自动执行。

### 4.5 接口

- `DesktopTask.priority` 保持「文件里的 `!n`」语义不变，保证旧客户端与现有写入逻辑不受影响。新增 `priority_source: explicit | heading` 与 `heading_priority`（`level`、`label`、`heading`、`heading_line`、`clamped`）。前端的有效档位为 `priority ?? heading_priority?.level`。
- `todo list --json` 输出同样的字段；纯文本输出在推断值后加 `(标题)`。
- 落地时同步修改 `PRODUCT.md` 的象限条目与 `docs/priority-quadrant-spec.md` §1、§8，写明 4.1 的界定，避免规格互相矛盾。

### 4.6 暂不做

写在正文开头的标签（`- [ ] [P1] 修复…`）不在本规格范围内。如需支持，其优先级应位于 `!n` 与标题之间。
