# TODO.md 格式规范 v1

> 状态:v1 草案(2026-08-30)。本规范是解析器、回写器、CLI、插件与 agent 的唯一格式依据。
> 设计依据见 `research/b-markdown-local-first-tools.md` 的坑清单与可借鉴设计、`research/g-decisions-addendum.md` 的决策记录。

## 0. 设计原则(不可违反)

1. **GFM `- [ ]` 是地基**:任何符合本规范的文件,在 GitHub / Obsidian / 任意 markdown 渲染器里都必须是一份可读的清单。
2. **人写的一切都要保住**:文件里的说明段落、表格、图片、代码块、HTML 注释、mermaid 图,工具一律原样保留。工具只改它自己认识的那几行。
3. **语义挂稳定标识符,不挂显示文本**:列的显示名可以是任意语言,行为由固定枚举决定。
4. **不可见字符不承载语义**:行尾空格、变体选择符等一律不作为语法。
5. **格式不做用户可配置项**:日期一律 ISO 8601。同一文件在任何机器上解析结果必须一致。
6. **纯 UI 状态不入文件**:列折叠、滚动位置、窗口大小等存本地 SQLite,不写进 markdown。

## 1. 文件结构

```markdown
---
todo-spec: 1
columns:
  - {id: todo,  name: "待办"}
  - {id: doing, name: "进行中"}
  - {id: done,  name: "已完成", type: done}
---

# 项目任务

这里是自由文本。工具不会碰这一段。

## 待办

- [ ] 实现解析器 <!--t:a1b2c3--> #core @me 📅2026-09-10 ^1000
- [ ] 写 CLI 骨架 <!--t:d4e5f6--> #cli ^2000

## 进行中

- [ ] 保真回写 <!--t:g7h8i9--> #core 🔗abc1234..def5678 ^1000

## 已完成

- [x] 建仓 <!--t:j0k1l2--> ✅2026-08-30 ^1000
```

### 1.1 frontmatter

- `todo-spec: 1` — **文件的身份标记**,必需。没有它的 markdown 文件不被本工具视为任务文件(避免误伤用户的普通笔记)。
- `columns` — 列定义。`id` 是稳定标识符(ASCII,语义锚点);`name` 是显示名(任意语言,用户可随便改);`type` 可选,取值 `done`(移入该列的任务自动标记完成)。
- `completion-policy` — 结局说明策略,可选值为 `normal` 或 `strict`,缺省为 `normal`。`normal` 下完成说明可选、部分完成与失败说明必填;`strict` 下三种结局说明都必填。字段名固定使用连字符,不得写成 `completion_policy`。
- frontmatter 中未被本规范定义的键**必须原样保留**。

### 1.2 列(column)

- 列 = `## ` 二级标题,其显示文本必须匹配某个 `columns[].name`。
- 匹配不上的 `## ` 标题**不是列**,是用户的普通章节。**其下的任务一律是游离任务(`column: null`)**,不继承上游列。
  - 修订理由(v1 起草时的错误,已在实现验证中暴露):原稿写「归属最近的上游列」,实测会导致用户自己的章节若恰好位于「已完成」列之后,其下 `- [ ]` 未完成任务被判定属于 `done` 列 —— **列归属说它完成、checkbox 说它未完成,两个事实源自相矛盾**,会污染看板渲染与对账引擎的判断。
  - 游离任务:CLI 可列出(`todo list --all`),**不参与看板列渲染**,不参与「移动到某列」类操作(需先显式归位)。
  - 例外:`## ` 标题之前(文档开头、frontmatter 之后)的任务同样是游离任务。
- 列的顺序 = 文件中出现顺序 = 看板从左到右顺序。

### 1.3 任务(task)

一行一个任务,形如:

```
- [ ] <正文> <!--t:ID--> <元数据 token>*
```

- `- [ ] ` / `- [x] ` — GFM checkbox。`[ ]`=未完成,`[x]`=完成。
- **非标准 checkbox 字符(`[-]`、`[/]` 等)**:CommonMark/pulldown-cmark 不把它们识别为 task list item,因此**这些行不会被解析为任务**。v1 的确定行为是:
  - 解析器**必须**在文档级别扫描出这类行,记录为 `unrecognized_task_like_lines`(行号 + 原文),**但不作为任务**;
  - 字节不动(它们只是普通列表项,回写时原样保留);
  - `todo lint` **必须**对它们发出警告:「第 N 行看起来是任务但使用了非标准 checkbox 字符,本工具不管理它」。
  - 理由:**静默不可见比不支持更危险** —— 用户(尤其从 Obsidian Tasks 迁移来的)会以为任务已被接管,实际上工具完全看不到它。v2 再决定是否提升为一等状态。
- 缩进的任务行 = 子任务(按缩进层级形成父子关系),缩进单位以文件内首个缩进任务为准并保留原样。
- **代码围栏(``` 与 ~~~)内、行内代码 `` ` `` 内的任何内容都不是任务。** 解析器必须先做围栏/行内代码排除。

## 2. 稳定 ID(最重要的字段)

```
<!--t:a1b2c3-->
```

- 载体是 HTML 注释,理由:GitHub/Obsidian 渲染时不可见,不污染人类阅读;而 emoji/特殊符号方案会污染。
- `t:` 前缀 + ID 值。ID 由 `[0-9a-z]{6,}` 组成(base36),**全局唯一**。
- **生成方式:随机 base36**(不用自增,避免多 agent / 多分支并发时撞号;参考 beads 的 hash ID 教训)。默认 6 位,冲突时自动加长。
- ID 是**任务的身份**:重命名、移动列、移动文件都不改 ID。所有外部引用(CLI、插件、对账记录、跨文件链接)只认 ID。
- **没有 ID 的任务行是合法的**(用户手写的新任务)。工具在下一次写入该行时补 ID;只读命令不得为了补 ID 而改文件。

## 3. 元数据 token

全部位于任务行尾,以空格分隔。**解析规则:从行尾向前逐个剥离已知 token,剩下的就是正文**(借鉴 Obsidian Tasks,无需分隔符)。

| token | 语法 | 含义 | 备注 |
|---|---|---|---|
| 标签 | `#tag` | 分类标签 | 可多个;**独立 token,不用逗号串**(逗号串在并发合并时丢数据) |
| 负责人 | `@name` | 指派 | 可多个 |
| 截止 | `📅YYYY-MM-DD` | 截止日期 | ISO 8601,**不可配置** |
| 完成时间 | `✅YYYY-MM-DD` | 完成日期 | 标记完成时写入 |
| 优先级 | `!1`..`!4` | 1 最高 | 缺省=无优先级 |
| 排序 | `^<整数>` | 列内排序键 | **分数式**:插入两卡之间取中值,拖动一张卡只改一行 |
| 物证 | `🔗<sha>..<sha>` | 关联 commit 范围 | 对账引擎的核心依据 |
| 依赖 | `⛔<ID>` | 被指定任务阻塞 | 可多个 |
| 引用 | `→<相对路径>#<ID>` | 指向分类文件中的任务 | 见 §5 |
| 进度 | `◐<1-99>` | 部分完成百分比 | 见 §3.1 |
| 失败 | `⚠<YYYY-MM-DD>` | 最近一次尝试失败的日期 | 见 §3.1 |

规则:
- 未知 token **原样保留在原位**,解析为 `unknown_tokens`,回写时不得丢失。
- emoji token 必须容忍可选的变体选择符 `\uFE0F`(解析时归一化,回写时保留原字节)。

## 3.1 部分完成与部分失败

单个任务的中间状态由两个**相互独立**的 token 表达,任务行本身仍是标准 GFM checkbox。

```markdown
- [ ] 给登录接口加限流 <!--t:p5pxad--> !1 ◐60 ⚠2026-09-01
      ↳ 令牌桶已实现并过单测;压测 500QPS 未过 <!--n:p5pxad-->
```

### 3.1.1 进度 `◐`

- 取值范围 **1–99**。`◐0` 与 `◐100` 不是合法进度 token,按未知 token 原样保留。
  - 理由:`0` 与「未开始」无法区分;`100` 会成为「已完成」的第二种写法,而完成状态只能由 checkbox 表达(§6.5.4)。
- **`◐` 永远不蕴含完成**。已勾选任务上的 `◐` 无意义,标记完成时由写入方清除。
- 进度是**声明**,不是核实结果。对账引擎不得依据 `◐` 推断完成。

### 3.1.2 失败 `⚠`

- 语义是「最近一次尝试出现失败,且尚未解决」,ISO 8601 日期。
- 与 `◐` 正交:一个任务可以同时是 80% 完成且带未解决的失败。
- **记录失败不改变完成状态**。`⚠` 出现在已完成任务上是对账信号,不是自动取消完成的依据(§6.5.4 状态只升不降)。

### 3.1.3 说明行 `↳`

行尾 token 承载不了散文,因此需要一条说明行,回答「做完了哪部分、还差什么、为什么失败」。

```
<任务缩进><6 个空格>↳ <文本> <!--n:<任务ID>-->
```

- **必须紧邻任务行的下一行**,且 `n:` 锚点必须等于该任务的 ID。两个条件缺一不可:
  - 没有锚点,说明行会在任务被移动后静默改嫁给相邻任务,让错误的任务开始汇报别人的状态;
  - 允许跨行查找,会把用户自己的段落误收为说明行。
- 一个任务**最多一条**说明行。重复设置是替换,不是追加。
- 缩进 6 空格使其成为该列表项的**惰性段落续行**。缩进代码块不能中断段落,因此它在任何 CommonMark 渲染器里都是列表项的一部分,不会变成代码块。已用 pulldown-cmark 实测:两个 checkbox 仍被识别为 task item,代码块数为 0。
- 文本中**不得出现 `<!--` 或 `-->`**,否则说明行可以伪造或吞掉自己的锚点。
- 任务被删除时,其说明行**必须**一并删除;否则会留下一条锚点指向已不存在 ID 的孤儿行。

### 3.1.4 兼容性

三个语法都是**纯增量**:不认识它们的旧解析器把 `◐`/`⚠` 当未知 token 原样保留,把 `↳` 行当普通续行文本保留。因此 `todo-spec` 仍为 `1`,不需要版本升级。

## 4. 回写规则(实现红线)

1. **只做字节区间外科手术**:用 pulldown-cmark 的 `OffsetIter` 取每个任务行的字节区间,按区间替换。**任何情况下都不得从 AST 重新序列化整个文件**(实测 cmark 726→702 字节丢内容,comrak 会注入合成注释)。
2. **未触碰行必须逐字节不变**,包括行尾空白、缩进风格、换行符类型(CRLF/LF)、BOM。
3. **写前乐观锁**:记录读取时的 mtime + 内容 hash;写入前重新校验,不一致则重新解析并 rebase 本次变更,绝不覆盖。
4. **原子写**:写临时文件 + `rename()`。
5. **写入串行化**:所有写入者(CLI / GUI / API / 插件 / agent)共用同一写队列与 advisory lock。
6. **写后校验**:若实际改动的行集合超出「预期变更集合」,**中止并报错**,不写入。
7. **冲突标记降级**:检测到 `<<<<<<<` / `=======` / `>>>>>>>` 时进入只读模式并明确提示,不解析、不崩溃。

## 5. 分类拆分(v1 预留语法,MVP 不实现)

文件膨胀时,按分类拆到 `todos/<分类>.md`,TODO.md 保留引用行:

```markdown
## 待办

- [ ] 认证模块相关 →todos/auth.md#a1b2c3
```

- **权威归属:任务行所在文件为准。** TODO.md 中的 `→` 引用行是**指针**,不携带可漂移的状态(不带 `[x]`、不带截止等)。
- 校验(`todo lint`,结构层零误报):死链(目标文件/ID 不存在)、孤儿文件(`todos/` 下未被引用)、重复 ID、引用与目标不一致。

## 6. 兼容性

- **Obsidian Tasks**:其 emoji 元数据(📅✅🆔⛔)语义与本规范一致或可映射;导入时把 `🆔xxx` 映射为 `<!--t:xxx-->`。
- **Obsidian Kanban**:列=`## 标题`、卡片=`- [ ]` 的约定与本规范一致,可直接读取其看板文件(其 `%% kanban:settings %%` 块作为未知内容保留)。
- **纯 GFM 文件**:没有 frontmatter 的普通 `- [ ]` 清单,可用 `todo init --adopt` 显式接管(加 frontmatter 与 ID),不自动改写。

## 6.5 对账引擎的不可协商约束(规范级)

以下属**产品安全底线**,任何实现不得违反。写进 spec 而非仅存于沟通记录,是因为这些规则比实现更重要,且必须能被后来者与其他 agent 读到。

### 6.5.1 证据不可销毁(最高优先级)

**对账引擎在任何情况下都不得删除 `🔗` 物证 token 与 `⛔` 依赖 token,`--apply` 亦然。**

理由:
- `🔗` 指向的 commit 被 revert,含义是「**你以为做完的工作被撤销了**」——这是用户最需要看到的诊断信号,也正是对账引擎存在的意义。删除它等于发现火灾后把火警拆掉。
- 删除后该任务退化为一个没有物证的普通未完成任务,**下次对账再也无法发现同一问题**,漂移被永久掩埋。这比不做对账更糟,因为它在「已检查」的假象下丢失了信息。
- `⛔` 失效的成因不唯一:依赖任务被删(删除合理)、ID 打错(应修正)、依赖移至他文件(应改为 `→path#id`)。引擎无法判定是哪一种,删除会抹掉「我曾在等待某物」这一信息。

### 6.5.2 confirmed 的语义是「事实确定」,不是「可自动修」

- `confirmed`:事实确定、非猜测。**不意味着可以自动修复。**
- 是否可自动修由 `suggested_action` 是否为空表达:
  - `confirmed` + `suggested_action != null`:可被 `--apply` 应用。**目前仅限一种** —— 无外部引用的重复 ID 重生成。
  - `confirmed` + `suggested_action == null`:死引用、孤儿依赖、失效物证、被撤销物证。**报告但不修**,正确动作需人判断。
- `suspected`:一切完成判定,以及修法不唯一的问题。`--apply` 永不触碰。

### 6.5.3 重复 ID 自动重生成的前置条件

允许自动重生成(保留首个、后续重生成),但:
- **重生成前必须检查外部引用**(`⛔<id>`、`→path#<id>`)。
  - **无外部引用**:`confirmed` + `suggested_action` = 重生成后续重复项。可被 `--apply` 应用。
  - **存在外部引用**:`confirmed` + `suggested_action = null`(**报告但不自动修**)。因为改 ID 会打断引用,而引擎无法判断引用原指哪一个。
- 报告须写明:保留了哪个、修改了哪个、新 ID 是什么。

> 修订说明(v1 起草时的自相矛盾,已更正):本节原写「存在引用时**降级为 suspected**」,与 §6.5.2 冲突。裁决依据 §6.5.2 的判据——`confirmed` 表示**事实确定**,`suspected` 表示完成判定或**事实本身存疑**。重复 ID 是确定的事实(两个任务确实共用一个 ID),不确定的只是修法,而「修法不唯一」已由 `suggested_action == null` 表达,不应再用层级重复表达一次;否则会把「事实确定但修法未知」与「事实不确定」混为一谈。
> 实际后果也支持此裁决:重复 ID 会静默破坏一切基于 ID 的操作,埋进 `suspected` 比留在 `confirmed` 更危险。

### 6.5.4 状态只升不降

未完成→完成需证据;完成→未完成**永不自动**。

**部分状态不构成例外。** `◐` 与 `⚠`(§3.1)都是声明,不是核实结果:
- 对账引擎**不得**把 `◐90` 读作「接近完成」而提升状态,也不得把 `⚠` 读作「其实没做完」而取消完成;
- 已完成任务上出现 `⚠` 是**报告项**,正确动作由人判断;
- 与 `🔗`、`⛔` 一样,`◐`、`⚠` 和 `↳` 说明行携带的是诊断信息,`--apply` 不得删除它们。物证有效**不等于**任务完成:用户常在开工时即写下物证,commit 存在只证明有人写了代码,不证明验收标准被满足。因此完成判定一律走 `suspected`。

### 6.5.5 不发明失效标记语法

物证失效是**对账报告的产物**,不是文件里的状态。不得为此新增 token 语法——格式层一旦写入用户文件就难以更改。

### 6.5.6 `--apply` 后必须报告未处理项

输出「已应用 N 项、跳过 M 项(需人工判断)」。否则 confirmed 中无自动修法的项会被静默忽略,成为新的漂移源。

## 7. 版本与演进

- `todo-spec` 值即规范版本。解析器遇到更高版本时:只读模式 + 提示升级,不尝试写入。
- v1 冻结后,新增字段一律走「未知 token 保留」通道向后兼容。
