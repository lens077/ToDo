Workspace / Project / Knowledge

将当前只能选择单个目录的 ToDo 应用升级为多项目虚拟工作空间。用户可以把不同磁盘路径、不同 Git 仓库中的项目加入同一个 Workspace。应用统一展示项目状态、环境、知识文档、任务、开发会话和待读资料。

Local-firstMarkdown-firstMulti-root WorkspaceAgent-nativeNo LLM APIIncremental Migration
本次修正的产品结论 Workspace 是逻辑容器，不是磁盘目录。Project 是稳定身份。Knowledge 是项目知识系统。Session 负责跨天恢复上下文。Task 是 Project 的子对象。Reading Context 是项目知识的外部资料层。

本方案面向实施 Agent。Agent 必须先审计真实仓库，再按阶段交付。本文不假设当前仓库使用某个前端框架、数据库、ORM 或桌面容器。所有技术决策以仓库审计证据为准。

产品要解决的真实问题

  1. 现在应用入口只能选择一个目录。用户无法把多个真实项目目录汇总到一个面板。
  2. 应用目前以 ToDo 为中心。它能读取 Markdown，却缺少稳定的项目档案。
  3. AI Agent 跨天工作时会丢失项目目标、架构决策、命令、环境和当前进度。
  4. 项目文档分布在 README、TODO、设计文档、实施计划、进度记录和运行手册中。
  5. 用户保存 X 和微信公众号文章时，容易忘记保存原因、关联需求和再次阅读条件。
  6. 应用不应该内置模型 API。应用应该提供标准化的上下文文件、Agent Skill、CLI 和验证协议。

产品边界

  • 应用管理多个目录的登记信息，不搬迁用户项目目录。
  • 应用扫描和索引已有 Markdown，不强制统一文档命名。
  • Markdown 是可编辑事实源。HTML 是人类阅读视图。
  • 数据库管理对象身份、关系、索引和应用状态。
  • Agent 负责理解和更新项目内容。应用负责提供协议、工具和确定性校验。
  • 应用不自动执行构建、部署、迁移和其他有副作用的命令。

1. 重新定义产品模型

Workspace · 虚拟工作空间

聚合不同路径下的 Project。它提供统一入口、汇总面板、筛选和跨项目活动视图。

示例：Personal、Client Work、Open Source、Experiments。

Project · 项目档案

代表一个长期存在的代码库或工作项目。拥有稳定 ID、实际根路径、仓库信息、目标、技术栈和生命周期。

路径可以变化。项目身份保持不变。

Knowledge · 项目知识库

发现现有 Markdown，识别文档用途，建立索引和关联。通过统一阅读器呈现架构、进度、决策和运行资料。

不要求用户先整理成指定目录。

Session · 开发会话

记录一次 Agent 或人工开发过程。保存目标、已完成事项、决策、验证证据、未完成工作和下一步。

Session 是恢复上下文的基本单元。

Task · 项目任务

属于某一个 Project。任务可以跨多个 Session。全局任务视图是多个 Project Task 的聚合结果。

任务不再是应用的根对象。

Reading · 外部资料

保存文章、帖子、仓库和文档。记录保存原因、关注问题、复访条件，并关联 Project 和 Task。

阅读资料进入项目知识关系网。

1.1 对象关系

关系基数规则
Workspace ↔ ProjectN:M通过 WorkspaceProject。一个项目可以加入多个工作空间。
Project → Task1:N每个 Task 必须属于一个 Project。
Project → Session1:N第一版一个 Session 只属于一个 Project。
Project → Documents / Decisions / Environment1:N文档和环境记录通过 Project ID 归属项目。
Reading ↔ ProjectN:M文章可以服务多个项目。
Reading ↔ TaskN:M文章可以支撑多个任务。

2. Workspace：多目录虚拟容器

2.1 关键体验

当前“选择目录”入口应升级为“创建或打开 Workspace”。用户创建 Workspace 后，从任意磁盘位置添加项目。Workspace 只保存成员关系。它不要求项目目录位于同一个父目录。

  • 创建、重命名、归档和删除 Workspace。
  • 通过目录选择器添加已有 Project。
  • 一个 Workspace 可以聚合多个磁盘卷、多个父目录和多个 Git 仓库。
  • 支持把一个 Project 加入多个 Workspace。
  • 支持项目搜索、标签、状态筛选、排序和拖动排序。
  • 检测相同规范化路径、相同项目 UUID 和相同 Git remote。
  • 目录失效时显示 Missing。用户可以重新关联新路径。
  • 从 Workspace 移除项目只删除成员关系。
  • 从应用登记中删除项目需要独立确认。

2.3 项目去重策略

  1. 先比较规范化绝对路径。
  2. 再读取项目登记文件中的 Project UUID。
  3. 再比较 Git remote URL 和 Git root。
  4. 发现可能重复时展示现有项目记录。
  5. 用户确认后选择打开现有项目或创建独立项目。

Git remote 相同不代表项目一定相同。Fork、镜像和多个工作树可能拥有相同 remote。系统不得仅凭 remote 自动合并项目。

3.2 增加 Context Health（上下文健康度）

这是在原始创意上建议增加的能力。它不是 AI 评分。它由确定性规则计算。

  • 项目是否有明确目标。
  • 是否有当前进度记录。
  • 是否有可执行的下一步动作。
  • 最近 Session 是否有结束记录。
  • 运行命令是否存在。
  • 关键文档是否已分类。
  • 是否存在超过设定时间的过期状态。
  • 是否存在待处理的决策冲突。

Dashboard 显示具体缺失项。避免只展示一个无法解释的分数。

3.3 Project Overview 应回答

  1. 这个项目的目标是什么？
  2. 当前处于哪个里程碑？
  3. 上次做了什么？
  4. 当前有哪些阻塞？
  5. 项目如何运行和验证？
  6. 下一步执行什么？

4. Knowledge：兼容现有 Markdown 的项目知识系统

4.1 先发现，再映射，再补齐

  1. 扫描项目内 Markdown 文件。
  2. 读取文件名、目录、标题、Frontmatter 和内容特征。
  3. 提出逻辑分类建议。
  4. 展示分类理由和置信度。
  5. 用户确认文档映射。
  6. 建立索引并提供统一阅读器。
  7. 只对缺少的知识类型提供模板。
  8. 用户确认后创建新文件。

例如，项目已经有 docs/design/system-overview.md。系统应把它映射为 Architecture 文档。系统不应再生成一份重复的 docs/architecture.md。

4.4 Markdown 是事实源，HTML 是阅读视图

  • Markdown 文件可以在应用外编辑。
  • HTML 阅读视图由 Markdown 实时或增量渲染。
  • HTML 缓存可以随时重建。
  • 阅读器支持目录大纲、标题锚点、全文搜索、代码语言标记、复制、图片预览和相邻文档导航。
  • 页面显示源文件路径、最后修改时间、文件状态和分类类型。
  • HTML 渲染执行 Sanitizer。禁止脚本、危险 URL scheme 和内联事件属性。

4.6 知识快照与状态新鲜度

增加“最近确认时间”和“信息来源”。例如环境信息来自 package.json，扫描时间为某日；项目进度来自某个 Session；运行命令来自 README。用户可以判断内容是否过期。

  • 每个结构化字段记录 source 和 updated_at。
  • 扫描结果不能静默覆盖用户确认值。
  • 关键状态可以标记为 stale。
  • 允许用户手动确认“当前信息仍然有效”。

5. Session：让 Agent 隔天能够恢复工作

5.1 生命周期

5.2 Begin 读取顺序

  1. 读取 Project Brief 和 Agent Instructions。
  2. 读取当前 Progress 和当前里程碑。
  3. 读取未完成 Task 和验收标准。
  4. 读取最近 Session 的总结和 Next Actions。
  5. 读取相关 Architecture、Decision 和 Runbook。
  6. 读取 Environment 声明和观测差异。
  7. 读取关联 Reading Context。
  8. 输出上下文摘要和本次工作边界。

5.3 Finish 写入内容

  • 本次目标和完成结果。
  • 修改文件和模块。
  • 新增或变更的架构决策及原因。
  • 执行的测试命令、结果和证据。
  • 未解决问题和风险。
  • 明确的下一步动作。
  • 关联 Task 状态更新。
  • Project Progress 快照更新。

6. Task：降级为 Project 子对象

  • Task 必须有 project_id。
  • 保留现有标题、描述、状态、优先级、标签、截止日期和排序字段。
  • 增加 acceptance_criteria、blocked_reason、source_session_id 和 updated_at。
  • Task 详情显示关联 Session、Decision、Reading 和文档。
  • 跨项目任务页面是聚合视图，不建立无归属的全局 Task。
  • 允许从 Reading、Decision 或 Session 创建 Task。
  • 任务完成必须有状态变化记录。关键任务可以要求验证证据。
旧数据兼容现有 ToDo 数据迁移到默认 Workspace 下的默认 Project。原任务 ID、标题、正文、状态、时间戳和排序必须保留。

7. Reading Context：阅读资料与项目知识关联

保留现有 X 和微信公众号链接解析功能。Reading 不应成为孤立的稍后阅读列表。它应支持“现在保存、未来在正确的项目阶段重新使用”。

7.2 关联模型

  • 一个 Reading Item 可以关联多个 Project。
  • 一个 Reading Item 可以关联多个 Task。
  • Project Knowledge 页面展示相关 Reading。
  • Task 详情展示相关资料。
  • 支持从文章创建 Task。创建前确认项目、标题和验收条件。
  • 支持把文章标记为某个里程碑的参考资料。

7.4 解析与导出规则

  • 链接解析失败时仍然保存 URL、时间和用户输入的上下文。
  • 重新解析只更新来源元数据和正文缓存。
  • 重新解析保留保存原因、个人笔记、结论、关联和阅读状态。
  • 导出到 Project Knowledge 时生成 Markdown 引用卡片。
  • 引用卡片包含标题、作者、来源链接、保存原因、关联 Task 和笔记。
  • 导出前显示 Diff。默认新增文件或新增段落。
  • 原文缓存与用户笔记分开存储。

8. Agent 协议：不内置模型，提供可执行契约

8.1 设计目标

不同 AI Agent 使用同一套项目知识约定。Agent 读取仓库中的入口文件和 Skill。Agent 通过 CLI 读取上下文、更新 Session 和验证文档。

8.2 AGENTS.md 入口文件

# Project Agent Contract

## Before Work
1. Read the Project Brief.
2. Read the latest Progress record.
3. Read relevant Architecture and Decision documents.
4. Read Environment and Runbook before running commands.
5. Run `virgo context start` when the CLI is available.

## During Work
1. Keep Task status accurate.
2. Record decisions that change architecture or behavior.
3. Record commands and validation evidence.
4. Keep user-authored notes intact.
5. Keep credentials out of project documents.

## Before Finish
1. Run required validation commands.
2. Record test results and evidence.
3. Update the active Session.
4. Update Progress and Next Actions.
5. Run `virgo docs validate` when available.

Detailed workflow:
- .virgo/agent/SKILL.md
- .virgo/agent/WORKFLOW.md
- .virgo/agent/SESSION.md
- .virgo/agent/DOCUMENTATION.md

8.3 Skill 文件结构

.virgo/agent/
├── SKILL.md
├── WORKFLOW.md
├── SESSION.md
├── DOCUMENTATION.md
├── DECISIONS.md
└── templates/
    ├── session.md
    ├── decision.md
    ├── progress.md
    └── reading-reference.md

Skill 定义五个流程：begin、work、validate、finish、resume。Skill 内容保持 Agent 厂商无关。具体 Agent 的配置文件可以引用同一份规范。

8.4 文档冲突优先级

  1. 用户当前明确指令。
  2. 项目安全规则和 Agent Contract。
  3. 已确认的 Architecture 和 Decision。
  4. Task 验收条件。
  5. 一般开发约定。

发现冲突时，Agent 输出冲突文件路径、相关段落和影响。Agent 等待用户决策。Agent 不自动覆盖已确认决策。

10.1 数据职责边界

  • 数据库保存 ID、状态、关系、索引、排序和应用配置。
  • Markdown 保存项目说明、架构、决策、Session、运行手册和用户笔记。
  • Git 负责版本管理和协作历史。
  • HTML 作为渲染结果和阅读体验层。
  • Reading 原文缓存复用现有存储。避免重复保存多份正文。

10.2 搜索能力建议

第一版先实现文件名、标题、Frontmatter 和正文的本地全文搜索。优先复用现有数据库的 FTS 能力。暂不引入向量数据库。后续可以基于用户实际检索行为评估语义搜索的收益和资源成本。

11. UI 信息架构与设计方向

参考用户提供的四个视觉方向：Lumière Desk 的克制型桌面工作台、Project Workspace Dashboard 的项目卡片布局、MDViewer 的文档阅读体验、Pieces 的上下文记忆组织方式。以下是产品信息架构，不是对参考作品的像素级复制。

11.2 Overview 汇总面板

  • Workspace 总数和 Project 总数。
  • Active、Paused、Maintenance、Completed 项目数量。
  • 跨项目未完成 Task 数量。
  • 需要恢复的 Session 数量。
  • 过期上下文和 Missing Path 数量。
  • 近期 Decision 和 Reading 更新。
  • 每个项目的下一步行动。

11.3 Workspace Dashboard

顶部展示 Workspace 名称、描述、项目数量和添加项目操作。主体展示项目卡片。卡片显示项目名、技术栈、生命周期、当前里程碑、下一步、最近活动和路径状态。支持状态筛选和最近活动排序。

11.4 Project Detail

  1. Overview：目标、进度、阻塞、下一步、最近 Session。
  2. Tasks：项目内任务列表和看板。
  3. Environment：声明环境、扫描环境、命令和差异。
  4. Knowledge：文档索引、分类、全文搜索和阅读器。
  5. Sessions：历史会话、恢复入口和上下文完整度。
  6. Activity：任务、决策、资料、文档和路径变更时间线。

11.5 Reading 页面

  • 列表显示标题、来源、状态、关联项目和保存原因摘要。
  • 详情展示正文、个人笔记、关注问题和复访条件。
  • 操作包括标记已读、稍后阅读、归档、关联项目、关联任务和导出引用。
  • 保存链接时允许先不填写保存原因。Inbox 提醒用户补充。

11.6 交互细节

  • 空状态提供明确操作入口。
  • 扫描结果与写入操作分离。
  • 文件写入显示 Diff、备份位置和撤销操作。
  • 危险操作显示受影响的项目、路径和数据。
  • 支持键盘导航、搜索快捷键和窗口尺寸变化。
  • 重要状态同时使用文字和图标表达，不只依赖颜色。

12. 现有单目录 ToDo 迁移

12.1 迁移步骤

  1. 备份现有数据库和应用配置。
  2. 创建默认 Workspace。
  3. 把当前选中的目录登记为默认 Project。
  4. 生成稳定 Project ID。
  5. 为现有 Task 回填 project_id。
  6. 保留现有 Markdown 分析器。
  7. 保留 X 和微信公众号解析器。
  8. 扫描现有 Markdown 并展示分类映射。
  9. 展示数据迁移预览和冲突。
  10. 用户确认后执行数据库迁移。
  11. 执行数量、关联和内容一致性检查。

12.2 回滚要求

  • 数据库迁移前生成可验证备份。
  • 迁移使用版本化 schema migration。
  • 迁移脚本支持事务和重复执行保护。
  • 迁移不移动、不删除用户 Markdown 文件。
  • 回滚数据库时保留迁移期间产生的外部文档。
  • 迁移失败时恢复数据库并输出报告。

13. 安全、隐私和可靠性

风险实施要求
路径穿越规范化路径并验证目标仍位于 Project root。写入时检查符号链接。
秘密泄露跳过凭证文件。日志脱敏。只保存环境变量名称。
误覆盖文档先 Diff、备份和确认。默认不覆盖。
命令副作用显示命令、cwd 和影响。用户确认后执行。
Markdown XSSSanitizer 清理 HTML。禁止脚本和危险 URL scheme。
文件监听丢事件应用启动时增量扫描。使用哈希对账。
并发编辑写入前校验旧哈希。冲突时停止并显示 Diff。
重复项目路径、Project UUID 和 Git remote 多维检测。
数据损坏事务、备份、版本化迁移和启动一致性检查。

14. 分阶段实施计划

每阶段完成后输出改动文件、测试证据、已知问题和回滚方式。未经用户批准，不进入下一阶段。

Phase 0 — 仓库审计

只读。禁止修改业务代码。
  • 检查技术栈、目录结构、应用入口、路由、状态管理和 UI 组件。
  • 检查目录选择器、文件权限、文件监听和多目录支持。
  • 检查数据库、Task schema、迁移机制和持久化。
  • 检查 Markdown 分析器和 HTML 渲染器。
  • 检查 X / 微信解析、阅读状态和内容缓存。
  • 检查构建、打包、测试、E2E 和 CI。
  • 输出架构映射、数据映射、复用清单、风险清单和修订后的实施计划。

Gate：每个建议都引用真实代码文件和模块。等待用户审查。

Phase 1 — Workspace 与 Project Registry

  • 新增 Workspace、Project、WorkspaceProject。
  • 实现目录选择和项目登记。
  • 实现多根路径聚合、去重、Missing 和重新关联。
  • 将旧单目录入口迁移为默认 Workspace。

Gate：两个不同路径项目可以在同一 Workspace 中显示。移动路径后 Project ID 不变。

Phase 2 — Project Profile 与 Environment

  • 实现项目档案、生命周期、里程碑、阻塞和下一步。
  • 实现 Declared / Observed Environment。
  • 识别运行时、包管理器、服务、端口和命令。
  • 实现敏感文件排除和命令授权。

Gate：扫描结果不覆盖用户声明。秘密值不进入数据库和日志。

Phase 3 — Knowledge 文档发现和阅读器

  • 扫描 Markdown 并提出分类。
  • 实现用户确认映射和增量索引。
  • 实现 Markdown HTML 阅读器和安全渲染。
  • 实现模板预览、Diff、备份和确认写入。

Gate：现有文档不搬迁、不覆盖。HTML 可由 Markdown 重建。

Phase 4 — Session 和上下文恢复

  • 实现 begin、finish、resume。
  • 实现 Session 与 Task 关联。
  • 实现 Session 模板、历史列表和恢复摘要。
  • 确定性收集 Git diff、测试结果和任务状态。

Gate：应用重启后能恢复最近 Session、未完成事项和下一步动作。

Phase 5 — Agent Contract、Skill、CLI 和 Validator

  • 生成 AGENTS.md 和 Agent Skill。
  • 实现 CLI 和稳定 JSON 输出。
  • 实现 ERROR、WARNING、INFO 规则。
  • 提供 Git Hooks 和 CI 模板。
  • 支持 advisory 和 blocking 策略。

Gate：CI 能阻断 ERROR。至少验证两种 Agent 接入方式。

Phase 6 — Reading Context 融合

  • 保留 X 和微信解析器。
  • 增加保存原因、关注问题、复访条件和个人笔记。
  • 增加 Project / Task 多对多关联。
  • 增加知识页展示和 Markdown 引用导出。

Gate：解析失败仍能保存。重新解析不会覆盖个人上下文。

Phase 7 — 汇总面板和 UX 收敛

  • 实现 Overview 和 Workspace Dashboard。
  • 实现项目卡片、筛选、排序和跨项目活动。
  • 实现上下文过期、缺失路径和未分类文档提示。
  • 完成键盘操作、空状态、错误状态和桌面窗口适配。

Gate：用户可以从汇总面板判断每个项目的状态和下一步。

15.1 主流程 E2E

  1. 创建 Workspace。
  2. 从两个不同路径添加两个 Project。
  3. 扫描并确认 Markdown 文档映射。
  4. 为其中一个 Project 创建 Task。
  5. 保存 X 或微信公众号文章并填写保存原因。
  6. 把文章关联到 Project 和 Task。
  7. Agent 执行 context start 并读取上下文。
  8. Agent 修改代码并执行验证。
  9. Agent 执行 session finish。
  10. 重启应用并恢复项目状态。
  11. CI 运行 Validator 并输出报告。

16. Agent 执行总提示词

将以下任务说明交给代码 Agent。Agent 第一轮只能完成 Phase 0。

你是本项目的 Staff Engineer 和实施负责人。
目标：把当前只能选择单个目录的 ToDo 应用升级为多项目 Workspace 和 Project Knowledge 系统。

执行规则：
1. 先审计真实仓库。不得假设技术栈和数据模型。
2. Phase 0 只读审计。不得修改业务代码。
3. Workspace 是逻辑容器，可以聚合任意真实目录下的 Project。
4. Project ID 稳定。项目路径变化不改变 Project ID。
5. Task 必须成为 Project 的子对象。
6. 先发现和映射现有 Markdown，再提出缺失模板。
7. Markdown 是事实源。HTML 是生成阅读视图。
8. 保留现有 ToDo、X 和微信解析能力。
9. Reading 必须记录保存原因、关注问题、复访条件、个人笔记和项目任务关联。
10. Session 必须记录目标、完成项、决策、验证证据、未完成项和下一步。
11. 不接入 LLM API。
12. Agent 集成采用 AGENTS.md、Skill、CLI、Validator、Git Hooks 和 CI。
13. 所有文件写入先展示 Diff。
14. 所有有副作用命令先展示命令、工作目录和影响，并等待授权。
15. 只记录环境变量名称。凭证值不进入数据库、日志或 Markdown。
16. 每阶段完成后执行测试并提交证据。
17. 未经用户批准，不进入下一阶段。

Phase 0 必须检查：
A. 技术栈和目录结构。
B. 应用入口、目录选择器和文件权限。
C. 数据库、Task schema 和迁移方式。
D. Markdown 分析器和阅读器。
E. X / 微信解析和 Reading 数据结构。
F. 文件监听和多目录支持能力。
G. UI 路由、状态管理和组件。
H. 单元测试、E2E、构建和 CI。
I. 新旧数据模型映射。
J. 风险、可复用模块和真实改动文件清单。

Phase 0 输出：
1. 当前架构图。
2. 当前数据模型图。
3. 当前功能到新模型的映射表。
4. 可复用模块清单。
5. 迁移风险和回滚方案。
6. 按真实代码修订的分阶段实施计划。
7. 每个结论对应的文件路径和代码证据。

完成 Phase 0 后停止。等待用户批准。
后续每个 Phase 输出：目标、改动文件、数据迁移、测试命令、测试结果、验收证据、回滚方式和未解决风险。

17. 待确认决策与默认建议

问题默认建议原因
一个 Project 是否能加入多个 Workspace？支持同一项目可能同时属于 Personal 和 Client Work。
一个 Session 是否能跨多个 Project？第一版单 Project降低上下文边界和数据关系复杂度。
是否强制统一 Markdown 目录？不强制先兼容用户现有文档习惯。
是否内置 LLM？不内置产品提供 Agent 标准和工具，不承担模型调用。
是否先做向量搜索？暂缓先验证全文搜索和上下文流程的实际价值。
Git Hook 是否强制？本地提示，CI 可阻断Hook 可以绕过，CI 可通过分支保护执行门禁。
是否自动执行运行命令？每次显示命令并授权避免意外修改本机和远程环境。
是否自动创建缺失文档？先预览，再确认避免生成重复文档和破坏原有结构。
最终产品定位这不是一个增加了项目卡片的 ToDo。它是一个本地优先的多项目工作台。它把项目身份、项目知识、开发会话、任务和外部资料组织在同一上下文中。它通过 Markdown 和 Agent 契约，让人和不同 AI Agent 可以持续接力开发。
