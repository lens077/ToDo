§2M1 · Session–Task 关联闭环 已实现并验证

D-M1-1 关联关系存哪里

选项 A session Markdown 加一节｜B 独立 JSON/SQLite 映射表
决定 A：## Task Links 节，每行一个 - <id>；Markdown 仍是唯一事实源，无 schema 迁移。
理由 会话文件即事实源是既有架构（session.rs:1-8）；加一节保持「文件可手读、Git 可追史」，与现有 extract_section_list 解析器零成本复用。

D-M1-2 resume 解析任务状态的来源范围

选项 A 仅项目根 TODO.md｜B 走 project.rs 多来源发现
决定 A（v1）：只解析根 TODO.md；找不到的 ID 显示「未在根 TODO.md 找到」，不报错。
理由 resume 必须在任何项目形态下工作（含非 git、无模板）；B 会把 session 模块耦合进 discover 机制（低耦合约束）。多来源项目里其他 Task Source 的任务暂显示未找到——功能可用，只是信息不全。
锚点 session.rs::resolve_linked_tasks()
如何修改 升级到 B 时只改这一个函数（换成 ProjectBackend 发现 + 逐源查找），返回类型不变。

D-M1-3 关联发生的时机

选项 A begin 时声明｜B finish 时记录｜C 两者都允许
决定 B：仅 finish --task <id>（可多次）记录；begin 不带任务。
理由 关联的语义是「本次会话实际做过什么」，事后记录比事前声明准确；避免「声明了没做」的空链接。
锚点 CLI main.rs SessionCommand::Finish 的 --task 参数；Tauri session_finish 经 SessionFinishInput.task_ids（serde default）自动透传，无壳层改动
如何修改 若要 begin 也声明：给 begin() 加可选参数并在 render_active() 预填节内容即可。

§3M2 · 审批确认对象（Outbox-lite） 已实现并验证

D-M2-1 参数摘要（digest）算法与计算方

选项 A 宿主自算摘要传入｜B ToDo 对 params 规范化 JSON 计算 SHA-256
决定 B：ToDo 侧对 params 做键排序、去空白的规范化后取 SHA-256（小写 hex）；宿主声明的摘要一律忽略。
理由 计算方与校验方同一，才杜绝「摘要与参数不符」的伪造面；规范化让 {"a":1,"b":2} 与 {"b":2, "a":1} 等价，宿主序列化差异不影响审批。
锚点 ai.rs::canonical_params_digest() + normalize()（params_digest 只在此产生）；依赖 sha2 0.10.9（已在依赖树中，锁文件仅 +1 行）
如何修改 换哈希/规范化规则只改这一个函数；改算法会使存量确认对象的旧摘要失效（安全方向失效，可接受）。

D-M2-2 门禁语义与错误码

选项 A 盲 ack 静默通过｜B 缺摘要与错摘要都拒绝（exit 1）｜C 新增退出码
决定 B：缺摘要 → Error::AiConfirmationRequired；不匹配 → Error::AiParamsChanged(期望值)；均 exit 1 + JSON 错误信封。宿主以新参数重发（event_at 更新）自动清 acked_at——旧审批失效复用既有规则 2。
理由 不新增退出码，避免破坏 AGENTS.md 已固化的 exit-code 契约；门禁在锁内校验（modify 闭包改为返回 Result），无 get/ack 竞态窗口。
锚点 ai.rs::ack()、error.rs 两个新变体、main.rs ack --confirm-digest、serve.rs AiAckInput.confirm_digest
如何修改 放宽/收紧只动 ack() 一处；桌面端 ops.rs::ai_ack 已带透传参数。

§4M3 · 确定性验证器 已实现并验证

D-M3-1 白名单范围——Virgo 自己跑哪些检查

选项 A 三项确定性检查（lint/对账结构层/docs validate）｜B 加上项目测试命令（make check 等）｜C 不自动跑
决定 A。明确不执行项目任意测试/构建——session.rs:1-8 的「app never runs tests」原则保持不变：agent 自报的命令行在前，Virgo 行在后，两者在表里天然分层可审计。
理由 三项检查都是本 CLI 自己的确定性逻辑（无外部命令、无网络、秒级），越权风险为零；而跑 make check 需要完整工具链与数分钟阻塞，属于 Agent 宿主的职责。
锚点 session.rs::run_virgo_checks()（唯一新增函数；finish() 在写表前调用）
如何修改 增删检查项只改这一个函数；不想自动验证时删除那一行 extend 即可整体关闭。

D-M3-2 检查失败的处理

决定 记录不阻断：任何检查出错/发现 findings 都如实写行（如「1 个重复稳定 ID」「N findings, M 项检查未运行」），finish 永远成功；无 TODO.md 的项目 lint 行显示「跳过」。
理由 finish 是会话收尾动作，阻断它会逼 agent 不写总结——那比缺验证更糟；行内如实的失败描述本身就是证据。
锚点 run_virgo_checks() 全部 unwrap_or_default()/match Err 分支

D-M3-3 行的位置与来源标注

决定 agent 行在前、virgo 行后附；每行 evidence 固定为 virgo 自动（确定性检查，非 agent 自报），一眼区分自报与机检。
锚点 finish() 的 validation_rows 组装；测试 finish_appends_deterministic_virgo_validation_rows 断言行序

§5M4 · Knowledge 全文搜索与增量扫描 已实现并验证

D-M4-1 搜索引擎与分词

选项 A FTS5 默认分词器｜B FTS5 trigram｜C FTS5 + CJK 字间插空格（短语查询）
决定 C：默认分词器把连续中文当作一个 token（「普通」搜不到「普通正文」），trigram 又要求查询 ≥3 字；采用经典 CJK 方案——索引与查询两侧都在 CJK 字符间插入空格，查询加引号成短语匹配，两字中文查询可命中；snippet 展示时反向去空格。用户输入逐词加引号，不可能注入 FTS5 语法（有专项测试）。
锚点 knowledge.rs：is_cjk/cjk_spaced/cjk_despace、knowledge_search()；FTS 表 knowledge_fts(doc_id UNINDEXED, title, body)
如何修改 换分词器只改 workspace.rs 迁移里的一行 DDL + 这三个辅助函数；索引由下次扫描自动重建，无需迁移数据。

D-M4-2 索引时机与 schema 演进

决定 随扫描重建：knowledge_scan 每次全量重读文件（≤2000 个、≤512KB，本来就全读），FTS 行 delete+insert——永远是「便宜且正确」的路径，不做部分增量数据结构；tombstone 同步从 FTS 删除。schema v3→v4（fail-loud 迁移框架内），存量索引行由下一次扫描自然补齐，无数据迁移。
理由 真正的增量（hash 对账跳过重解析）在 knowledge_documents 层已存在（content_hash）；FTS 层全量重建的成本远低于维护两套一致性逻辑。
锚点 workspace.rs::migrate()（SCHEMA_VERSION=4）、knowledge_scan() 的 FTS upsert 与 tombstone 清理

D-M4-3 文件变更的自动重建（watcher）

选项 A Rust 侧新 watcher 管道｜B 前端订阅既有事件 + 去抖
决定 B：ProjectDetailPanel 订阅既有的 desktop://snapshot-changed（打开项目的 watcher 已在发），5 秒去抖后重建索引；仅当用户本会话扫描过（documents 已加载）才触发，失败静默保留旧索引。mock/浏览器无事件，天然跳过。
理由 低耦合：不新建 Rust watcher 生命周期（Phase 0 审计 R4 的「事件风暴」用去抖+hash 跳过化解）；项目打开期间才有意义，面板正是「已打开项目」的自然作用域。
锚点 ProjectDetailPanel.tsx 的 rescan useEffect（监听 + 5s 去抖 + cancelled 守卫）
如何修改 想改去抖时长/搬去 Rust：改这个 effect 或替换成 Tauri 命令调用，其他层不动。

§6M5 · SQLite 投影接入决策 已代决策（数据驱动）

D-M5-1 是否把 SQLite 投影接入 serve/桌面端

背景 TODO.md b6r1vy：11-03 审计指出"投影未接入、无性能证据支撑决策"。本轮新建基准 benchmark_projection_10k_tasks（#[ignore]，可复跑）。
实测（release，10k 任务） 内存解析 59 ms ｜ 投影全量重建 28 ms ｜ 增量更新（1 任务翻转）132 ms
决定 暂不接入：内存快照以 10 倍余量满足"1k 任务 <100 ms"的原始门槛；增量路径甚至慢于全量重建——投影在此规模是无收益的第二数据面。
重开触发 活跃任务 >20k ｜ 常驻 serve 多客户端轮询成 CPU 热点 ｜ 快照 p95 >500 ms
锚点 DECISIONS.md 决策⑥（完整论证与接线点）；TODO.md b6r1vy 备注已用 todo note 更新（任务状态保留待你复核）
如何修改 推翻 = 按决策⑥末尾的接线点把 snapshot 路径换 Projection，数据层已就绪（测试全绿）。
