# 用户问题：TODO 漂移

**可证伪陈述**：独行开发者（或小团队）在 AI 编码工作流下，AI 直接修改代码与仓库，但任务的「待办真相」散落在多处——会话内 TodoList、聊天记录、脑内、外部看板——AI 完成后不回写看板，导致看板漂移、过期、失去信任，最终没人看，任务无法被持续追踪与复盘。

**触发场景与阻碍**：AI 每完成一段代码就「顺便」解决或新增了 TODO，但看板停留在旧状态；人在多个会话与看板之间来回切换，无法确认「谁真的做完了」。Claude Code 的待办清单是会话级的（\[F4\]\[F5\]），Codex 用户也普遍抱怨 Skill/Memory 需要自己维护、多 Agent 之间来回切（\[F30\]）。研究显示 78% 的 Agent 在多步推理中因上下文丢失导致任务失败率超 40%（\[F8\]），链式 20 步任务成功率降到 36%（\[F9\]）——「记不住做过什么」是 Agent 系统的结构性缺陷，也是看板漂移的根源。

**当前替代与后果**：有人用 GitHub Issues \+ commit 自动关联/关闭（\[F25\]），但无法覆盖代码内 TODO 注释与会话内待办；「记录不等于执行」是效率工具的通病（\[F26\]）。后果是任务流失、返工、失去单一事实源。

**反证与边界**：不使用 AI 编码的开发者没有此痛点；已有严格 Issues 流程的团队部分缓解。因此目标人群应锁定「AI 编码重度用户」。

# 市场与竞品深度测评

## monday\.com 拆解（用户点名参考）

**它是什么**：monday\.com 是「工作操作系统」（Work OS），以色彩化表格为数据底座，通过分组、筛选与多视图（看板、甘特图、时间线、日历）呈现工作数据，提供数百个模板与基于条件的自动化（如状态变更时通知负责人）（\[F2\]）。官网自述「Made for work, designed to love」，并把 AI 织入工作流，免费版不限时间（\[F3\]）。

**产品矩阵**：monday Work Management、monday dev（面向研发、对接 GitLab/GitHub）、monday sales CRM、monday service、monday marketer。

**商业验证**：订阅制、按席位收费；FY2025 营业总收入约 12\.32 亿美元、净利润约 1\.19 亿美元（\[F1\]）。这证明「可视化协作 \+ 订阅制」的付费意愿与规模是成立的。

**对本方案的启示**：借鉴其「多视图自定义 \+ 自动化 \+ 模板化启动」；但它真相在云端专有数据库，体量重、面向团队与企业，个人开发者无法让 AI 把仓库当作真相源——这正是本方案的差异化空间。

## 本地优先 / 开发者 TODO 工具

- **Taskwarrior / todo\.txt**：纯文本 / CLI、离线、极客友好，但没有看板、没有 AI 同步、没有 MCP。

- **Obsidian Tasks / Logseq**：本地 Markdown 待办，可扫描整个库的 \- \[ \] 并高级查询（\[F18\]）；Logseq 本地优先、支持 Git 同步（\[F19\]）。但无 git 仓库 TODO\.md 绑定、无 MCP 通道。

- **VSCode Todo Tree**：收集代码中 TODO / FIXME / NOTE 注释，侧边栏树形展示并可跳转代码行（\[F17\]）。是「读代码 TODO」的最普及方案，但只读、单编辑器、无看板与双向同步。

- **WeekToDo**：开源极简周计划，本地存储，跨平台（\[F28\]）。

结论：这类工具能「读」代码 TODO，但没有「双向看板 \+ AI 同步 \+ 校验」的能力，正说明用户设想的「看板只是编辑视图、真相在 MD」这一形态尚属空白。

## 是否存在雷同工具：结论

**严格意义上「仓库 TODO\.md 为真相源 \+ 双向同步看板 \+ MCP / Skills 供 AI 读写 \+ 防漂移校验按钮」的组合，截至 2026\-08\-30 的公开检索未发现已上线产品。**但三个相邻玩家（Vibe Kanban、Routa Kanban、Plane）已具备「本地/仓库亲和 \+ AI 执行」基因并快速演化，本方案不是蓝海，而是「窄缝 \+ 时间窗」。

**定位图**：X 轴为真相源（仓库/本地文件 ↔ 云端专有数据库），Y 轴为核心机制（追踪同步现状 ↔ 编排驱动执行）。

**图后含义**：左上区域（仓库真相 \+ 编排执行）是待验证空间，也是最可能被 Vibe Kanban / Routa 覆盖的方向；本方案建议从「仓库真相 \+ 强同步 \+ 校验」切入（左下偏中），先建立信任，再视需要向编排方向延伸。代价是：如果只做「同步」而不做「校验 / AI 主动维护」，差异化会被快速抹平。

# 竞品机制与战略分野

围绕用户任务提炼三个结构性分野，解释「为什么不同」而不是「哪里不同」：

1. **真相源落点**：仓库/本地文件 ↔ 云端专有数据库。决定 AI 能否把任务当作 repo 事实直接读写、能否进入 PR 评审、能否被 git 版本化与多端同步。云端看板（monday / Linear / Todoist）永远无法成为仓库内真相；本方案选择「repo 即真相」。

2. **核心机制**：追踪/同步现状 ↔ 编排/驱动执行。决定产品是「记录真实」还是「派活干活」。Vibe Kanban / Routa 走编排执行；本方案从「追踪 \+ 同步 \+ 校验」切入，与它们互补但存在被覆盖风险。

3. **数据主权与性能**：本地优先 / 离线（SQLite \+ watcher）↔ 云服务。决定启动速度、隐私、离线可用性与商业化形态。用户对性能敏感（启动 \<2s、编辑不卡），本地优先 \+ 增量索引是正确路线。

# 产品想法评审

## 成立的理由（优点）

1. 痛点真实且正在加剧：AI 编码已是主流工作流，会话级待办结构性易丢（\[F4\]\[F5\]\[F8\]\[F9\]\[F30\]），「看板漂移、没人看」是 AI 时代的新问题。

2. 定位一句话可讲清：「让 AI 改的代码和你看到的 TODO 永远一致」。对开发者有直觉吸引力。

3. 机制契合生态：MCP 是标准接入层（\[F16\]\[F23\]），仓库 TODO\.md 对 AI 天然可读可写，git 天然可版本化、可多端同步、可 PR 评审。

4. 技术可行且匹配性能诉求：Tauri \+ SQLite \+ watcher 是成熟组合（\[F21\]\[F22\]）。

## 风险与缺口

1. **工程硬骨头（生死线）**：TODO\.md 无损 round\-trip（格式多样：清单、分组、注释、表格、emoji 状态），AI 与人类并发改同一文件，冲突策略与「不破坏用户格式」是产品成败关键，也是大部分同类项目回避它的原因。

2. **注释扫描噪声大**：TODO / FIXME / XXX 格式杂、历史垃圾多，全量导入即灾难，必须做去重与分诊，否则第一印象崩。

3. **竞品时间窗**：Vibe Kanban / Routa / Plane 演化快，若差异化只是「同步」，很快被吸收。

4. **变现难**：个人开发者工具付费意愿弱，本地优先更难做订阅；需要「云同步 / 团队 / AI 校验额度」等付费钩子。

5. **范围蔓延**：需求清单很长（多仓库、注释扫描、REST、ntfy、i18n、web/PC/移动、商业化），全做必死，必须分阶段。

# 产品选项与取舍

## 目标用户

独行开发者、深度使用 Claude Code / Codex / Cursor 的 AI 时代开发者。P0 以内测方式面向「自己 \+ 同类开发者」冷启动，避免泛化人群。

## P0 能力（闭合一个关键任务）

- 单仓库 TODO\.md 无损解析与回写（round\-trip，回写后 git diff 为空）。

- 本地 SQLite 索引 \+ 文件 watcher（增量、启动 \<2s、交互 \<100ms）。

- 看板 UI（拖拽改状态即回写 TODO\.md）。

- MCP Server：CRUD \+ query \+ 校验（verify）工具，供 Codex / Claude / Cursor 接入。

- 「校验 / 强同步」按钮：让 AI 查询代码现实（git diff、commit、注释是否存在）与看板比对并修复漂移。

## 借鉴与差异化

|借鉴对象|借鉴点|差异化（本方案）|
|---|---|---|
|monday\.com|多视图自定义、自动化、模板化启动（\[F2\]）|真相在 repo 的 TODO\.md 而非云端专有 DB；AI 可直接读写同一事实|
|Vibe Kanban|git 工作流融合、worktree 隔离、本地优先（\[F10\]\[F11\]）|真相源 = 仓库 TODO\.md（而非自有 DB）；面向「同步防漂移」而非「派活给 AI」|
|Routa Kanban|把 codebase / worktree / 验证状态绑到卡片（\[F12\]）|面向个人「强同步真相」，不依赖多 Agent 编排基础设施|
|Claude Code / Codex|TodoWrite 待办、AGENTS\.md / CLAUDE\.md 项目约束、Skills 标准（\[F4\]\[F5\]\[F29\]）|把会话级待办持久化到仓库，让「项目约束 \+ MCP \+ Skills」三通道共同维护同一真相|

## Non\-goals（第一阶段明确不做）

- 多仓库自动导入与全量注释扫描（放到阶段二，且必须先解决分诊）。

- 移动原生 App（用 Web UI / PWA 覆盖）。

- 团队权限与多人实时协同。

- 通用个人待办、日历排程、非开发者市场。

# 能力路线图与验证计划

能力路线图回答：用户问题如何进入三阶段能力，每阶段的证据门与非目标。

## 验证方法（最小闭环）

- P0 原型在自己真实项目跑 2 周；基线指标：TODO\.md 回写后 git diff 为空的比例、MCP 闭环读写成功率、启动 / 交互耗时。

- 停止条件：round\-trip 无损率显著低于可接受阈值，或竞品在窗口期内已覆盖核心体验。

- 下一证据门：5 名外部开发者试用，观察「漂移报告」是否让看板重新被信任、是否愿意继续使用。

- 任何准确率 / 留存 / 转化阈值，必须先建立基线与测量窗口，再确认门槛，不预先填数。

# 商业化思考

- **模式建议**：开源核心（建立信任与传播）\+ 付费增值（云同步 / 多端、团队协作、AI 校验额度与周漂移报告、企业私有化）。

- **参照**：AI 应用约七成采用订阅制（\[来源见映射表\]）；monday\.com 以订阅制做到年收入 12\.32 亿美元（\[F1\]），验证了 B2B 付费意愿；Todoist 走个人订阅。

- **个性化作为吸引力**：AI 分诊代码注释、自然语言建任务、任务与 commit / PR 关联、每周漂移报告、自定义规则模板——这些是留存与口碑手段，不是核心卖点本身；核心卖点永远是「防漂移的强同步」。
