## 1. 本文解决什么问题

`调研文档/dk/` 已有三份对照文档，各自把一份来源文档与当前实现逐条比对。缺的是横向视图：三份文档提到的功能合并起来一共有多少条、哪些条是同一件事被说了三遍、哪些条仓库已经做完、哪些条仓库压根没记录。

本文提供三样东西：

1. **去重后的功能全集**（§5，共 109 条，分 13 个域）。其中 63 条来自三份文档，46 条是三份文档未提及的条目。
2. **重复与重叠清单**（§4），分四类：来源文档之间的重复、与仓库既有实现的重叠、同物异名、方向冲突。
3. **整合后的落位**（§8），把三份文档各自的路线图并入仓库既定顺序。

读者若只想看结论，读 §4 与 §8。

## 3. 术语归一

三份文档与仓库对同一件事使用了不同名字。整合时先对齐，否则会把同一条功能重复计数。

| 来源文档用词 | 仓库术语 | 权威定义位置 |
|---|---|---|
| 强同步 / 同步事实 / Sync Reality / 校验按钮 / 手动同步按钮 | **对账**（Reconciliation Finding） | `CONTEXT.md`、`docs/format-spec-v1.md` §6.5 |
| SQLite 缓存 / 索引 / 高速缓存中介 | **派生投影** | `README.md`、`crates/todo-core/src/projection.rs` |
| AST 解析与回写 / 双向实时同步 | **保真回写**（字节区间外科手术） | `docs/format-spec-v1.md`、`crates/todo-core/src/write.rs` |
| 看板仅为编辑入口 | **视图与安全编辑入口** | `docs/desktop-mvp-spec.md` §1 |
| 任务与 commit 关联 | **Evidence（物证）** | `CONTEXT.md` |
| 随想 / 快速记录 | **Capture / Triage** | `CONTEXT.md` |

**一条关键区别**：三份文档说的「强同步」隐含「工具自动把两边改成一致」；仓库的「对账」是「代码改动只是物证，完成是待核实的声明，引擎只报告」。名字接近，语义相反，详见 §4.4 冲突 2。

## 5. 整合后的功能总表

**编号约定**：本节的 ID 是本文自建编号，格式为域字母加序号（A1、B3、E10……），仅在本文内有效。带〔D〕前缀的 D1–D11 是 `research/g-decisions-addendum.md` 的决策编号，与本节的 D 域无关。

状态取值：

- **已交付**：仓库已实现，且在〔V〕有验证记录。
- **已规范未实现**：规范或决策已写死，代码未落地。
- **已决策后置**：已评审入档，排在既定顺序的后位。
- **已决策不做**：明确排除，含理由。
- **未覆盖**：来源文档提出，仓库无对应记录，需要新决策。

## 7. 仓库已有、三份文档均未提及的条目

这一节反向说明三份文档的覆盖盲区。§5 共 109 条中有 46 条属于此类，其中最值得单列的 21 条如下：

**工程安全面**：A3 稳定 ID、A4 身份标记、A6 格式规范与 lint、A7 接管存量清单、A10 未知内容保留、B4 并发写入安全、B5 乐观锁、B6 冲突标记降级、B7 写后校验。

**质量面**：M1–M4 测试与验证体系。

其中三条最关键：

1. **E2 物证绑定**。三份文档都想做对账，但都没回答「对账拿什么当依据」。仓库的答案是 `🔗sha..sha` 把任务绑定到 commit 范围，让对账从「让 agent 重新理解代码」降级为「比对物证与 HEAD」。
2. **D6 SessionStart 注入**。三份文档的接入方案都依赖 agent 主动调用工具；仓库的方案是会话开始时主动推送，不依赖 agent 记得。
3. **B4–B7 写入安全组**。三份文档都把回写当成一个功能，没有把它当成一个需要锁、需要校验、需要降级路径的子系统。

## 9. 现状披露：已实现项中的已知偏差

本文标注「已交付」的条目，其中若干在 `调研文档/dk/对抗/对抗0-captain终审总评.md` 的终审裁定中被认定与 `README.md` 表述存在偏差。整合时不应把 README 表述直接当作能力上限。

下表「终审编号」列的 F1–F18 来自那份裁定总表，与 §5 的 F 域（代码扫描与多源导入）无关。

| 本文条目 | 终审编号 | 偏差 |
|---|---|---|
| E2 Git 物证层 | F1（全案第一重） | shallow clone 或非 git 环境下物证检查整层跳过，human 输出、退出码、hooks 三个出口仍显示无异常；`applied 0, skipped 0` 中的 `skipped` 与报告里的 `skipped` 同词异义 |
| A7 接管存量清单 | F2 | `init --adopt` 逐行前缀扫描会给代码围栏内的示例注入 ID |
| B5 乐观锁 | F3 | 「检测到外部修改时放弃写入」未接线，退出码 5 为生产死码；`reconcile --apply` 在锁内重跑全量对账，竞态窗口无上界 |
| E3 语义层 | F5 | `--no-semantic` 当前是零行为差异的空开关且未标注 |
| A6 lint | F10 | lint 不检查重复 ID，而重复 ID 是格式规范 §2 的核心不变量 |
| — | F6 | `README.md` 声明的 Rust 1.74 与锁定依赖实际 MSRV（CLI 1.85、整仓 1.88）冲突 |

另有一项治理缺口（终审 F18）与本文 §4.4 冲突 2 直接相关：hooks 受管指令块要求 `evidence → todo done`，而〔R〕R4 建议 agent 完成后进 InReview 而非直接 Done。**「谁可写完成状态」目前不存在于任何规范性文件**，需要一份 ADR 拍板。在拍板前，本文 §4.4 冲突 2 的表述只覆盖对账引擎的行为，不覆盖 `todo done` 命令本身。
