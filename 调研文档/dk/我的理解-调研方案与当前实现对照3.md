# 我的理解：《想法评审与市场深度调研》与当前实现对照

> 写作日期：2026-08-31。对照对象：`调研文档/AI 时代开发者 TODO 工具：想法评审与市场深度调研.md`（下称「评审报告」，部分内容由豆包生成）与本仓库当前实现（commit `1669194`）。
> 依据：通读评审报告、`调研文档/1.md`、`research/` 报告集（README 与 g 补遗精读）、`DECISIONS.md`、`CONTEXT.md`、`README.md`、`docs/format-spec-v1.md`、`docs/desktop-mvp-spec.md`、`docs/verification-log.md`、`docs/adr/0001`；抽查 `crates/todo-core`、`crates/todo-cli`、桌面 host 源码（模型、回写、对账、hooks 为重点）；实跑 `target/debug/todo` 的 `list`、`reconcile` 确认可运行。
> 读者：需要判断「评审报告在多大程度上仍然作数」的维护者。先读 §1 结论与 §5 判断，逐项差异查 §4。
> 说明：同目录已有两份对照文档，分别针对《构建与评测》docx 与 `1.md`；本文是第三份，只对照评审报告。文中评价是我（claude-fable-5 会话）的独立结论。

## 1. 结论先行

1. 评审报告答对了三件事：痛点定性（TODO 漂移是结构性问题）、定位收窄（单仓库、本地优先、仓库内 `TODO.md` 为真相源、明确 non-goals）、技术路线（Tauri + SQLite 可行）。这些与当前实现一致。
2. 评审报告答错或已过时两件事：把 MCP 当作 P0 核心接入层（实现已按 `research/g-decisions-addendum.md` D1 决策去 MCP，改用 CLI + hooks）；把「校验」设计为按钮（更深一轮调研认定「按钮 = 用户要记得点 = 原痛点翻版」，实现改为默认只报告的 `todo reconcile` 加 SessionStart 自动注入）。
3. 评审报告标注的「最大不确定性」——无损双向同步的工程可行性——已被实现解决，并有独立验证记录背书。真正剩余的不确定性是它列的第二项：开发者是否愿意为「防漂移」付费。该项至今没有数据。
4. 建议今后以 `research/README.md` + `DECISIONS.md` + `docs/format-spec-v1.md` 为权威依据，评审报告降为历史参考。理由见 §2 与 §5。

## 2. 三层材料的关系：结论并不一致

仓库内的调研材料实际是三个时间层，后一层修正前一层，实现只遵循最后一层。

| 层 | 材料 | 核心主张 | 与实现的关系 |
|---|---|---|---|
| 早期评审 | 评审报告、`1.md` | 建议做；P0 = 无损回写 + SQLite + 看板 + **MCP Server** + **校验按钮** | 定性判断被采纳，接入方案被推翻 |
| 深度调研 | `research/`（5 个并行 agent，400+ 来源） | 对账引擎升级为核心卖点；看板降级为附赠视图；CLI > hooks > MCP | 实现的直接依据 |
| 拍板记录 | `DECISIONS.md`、`research/g-decisions-addendum.md` | D1 去 MCP；存储方案 A 起步、C 预留；随记进个人收件箱 | 实现逐条落地 |

评审报告与深度调研的两处硬冲突，可以说明它的证据质量：

- **竞品时效**：评审报告把 Vibe Kanban 当作在世竞品（F10、F11），`research/` 查明其已于 2026-04-10 关停，且死因（强制登录上云摧毁本地承诺、27,953 star 仍找不到商业模式）对本产品的「不登录也能完整使用」铁律有直接教益。评审报告漏掉了这一整条教训。
- **证据等级**：评审报告的关键数字多为二手转述——F8「78% 的 Agent 失败率超 40%」自标「转述学术结论」，来源集中于掘金、头条类文章；`research/` 则以官方 issue、源码、实测为准（如 Claude Code issue #39961 实测 50–75% 会话浪费在重做已完成工作、实测 27% 幽灵任务）。两者结论方向一致，但可引用性不同。

## 3. 当前实现状态（以独立验证为准）

crates 下约 4,200 行 Rust（不含桌面 host 与前端），9 个提交（2026-08-30 至 08-31）。`docs/verification-log.md` 记录了 captain（claude-opus-5）对实现方（openai/gpt-5.6-sol）的独立验证：不采信实现方自测，逐项用实现方未见过的样本复验，并以「注入缺陷确认测试变红」的方式检验测试本身有效。

| 层 | 内容 | 验证要点 |
|---|---|---|
| 格式规范 | `format-spec-v1.md`：frontmatter 身份标记、稳定 ID `<!--t:xxx-->`（随机 base36）、行尾 token（`#` `@` `📅` `✅` `!` `^` `🔗` `⛔` `→`）、§6.5 对账不可协商约束 | 两处规范缺陷由实现暴露后修订（非标准 checkbox、列归属） |
| todo-core | 无损解析（字节视图，永不 AST 重序列化）、外科手术回写、advisory lock + 乐观锁 + 原子写、SQLite 纯投影、对账引擎 | 恶意样本逐字节还原；16 进程并发写零丢失；千任务投影中位 8.99 ms |
| todo-cli | `init/adopt`、`list/add/done/undone/next`、`lint`、`evidence`、`reconcile`、`hooks`；`--json` 稳定 envelope；退出码 0–6 | TOCTOU 修复后 3,840 次并发创建零事故；退出码逐项验证 |
| 桌面端 | Tauri 2 直调 core（不 spawn CLI）、看板/今日/随记三视图、全局速记快捷键、文件 watcher | 冷启动实测 0.33–1.2 s（独立二进制 330.5–370.0 ms，bundle 首次 1204.9 ms，均低于 2 s 预算）；命令层 11 项契约测试，5 类历史缺陷注入均变红 |
| 接入层 | `todo hooks`：Claude SessionStart 注入任务快照与对账摘要（上限 40 行、2 s 超时兜底）；CLAUDE.md / AGENTS.md 指引块 | 指引块要求「先记起点 commit，完成后 `todo evidence` 再 `todo done`」 |

仓库已在用工具管理自身开发：`TODO.md` 中有带 `🔗` 物证的已完成任务与进行中任务，我实跑 `todo list --all` 与 `todo reconcile --no-semantic` 均正常（对账零发现）。

一个值得单独记录的过程事实：`--apply` 曾删除 `🔗` 物证 token，被验证方打回；根因一半在裁决只存在于聊天记录，此后「证据不可销毁、完成判定永远 suspected、状态只升不降、apply 必报未处理项」被写进 spec §6.5。规则从对话沉淀为规范，这个模式本身比单条规则更重要。

## 4. 评审报告 P0 清单逐项对照

| 评审报告 P0 项 | 实现状态 | 说明 |
|---|---|---|
| 单仓库 `TODO.md` 无损解析与回写（回写后 git diff 为空） | ✅ 已实现并验证 | 验证强于报告要求：未触碰行逐字节不变、写后校验超预期变更即中止、属性测试进 CI |
| 本地 SQLite 索引 + watcher（启动 < 2 s、交互 < 100 ms） | ✅ 已实现并实测 | SQLite 定位为纯投影、可随时重建，杜绝第二事实源；`list` 暂未接投影（实测瓶颈在进程启动，已记录触发条件） |
| 看板 UI（拖拽改状态即回写） | ✅ 已实现 | 定位按深度调研降级为「视图与安全编辑入口」；拖放只发 intent，Rust 回写成功返回新 Snapshot 才确认 |
| MCP Server（CRUD + query + verify） | ❌ 未做，且为主动决策 | D1：社区实证 CLI > hooks > MCP；`--json` 面即未来 MCP 的 schema，需要时以 rmcp 薄壳补上 |
| 「校验 / 强同步」按钮 | 🔄 变形落地 | 落为 `todo reconcile`（默认只报告）+ hooks 自动注入 + 桌面端只读展示 Finding；「让 AI 修复漂移」收窄为「结构层确定性检查 + 语义层预留接口」 |

报告之外，实现多做了：Capture 随记与 Triage 分拣（个人收件箱 `~/.todo/inbox.md`，不污染仓库）、`evidence` 物证命令（任务绑定 commit 区间，把对账从「重新理解代码」降为「比对物证与 HEAD」）、`lint`、`adopt` 接管存量清单、今日视图。

报告的 non-goals（多仓库、注释扫描、移动端、团队协同、通用待办）实现全部遵守，且额外排除了 MCP、账号、云同步。

验证计划对照：报告要求「P0 在真实项目跑 2 周基线，再给 5 名外部开发者试用」。目前 dogfooding 自 08-31 刚开始，启动与交互耗时两项指标已实测达标，round-trip 无损率尚无基线窗口数据，「MCP 闭环成功率」指标随 MCP 取消而作废。

## 5. 我的判断

**这个产品的护城河不是看板，是三件事的组合。** 一是物证机制：`🔗sha..sha` 让对账有可审计的确定依据，是逐条核查过的全类目空白。二是无损回写工程：评审报告认定的生死线，已被解决且难以速成复刻——同生态的对照实验（Obsidian Kanban 全文件重序列化毁数据而弃坑）说明这条线淘汰过前人。三是安全底线的克制：§6.5 那组「不可协商约束」决定用户信任，而信任崩塌一次就不会再开启对账。

**评审报告的正确用法是历史参考加需求池。** 它的定性结论（漂移结构性、真相源分野、窄缝加时间窗）已被更强的证据链重述，它的接入方案已被推翻，它的竞品情报有滞后。后续阶段性需求（多仓库、注释扫描、通知、商业化）应以 `research/` 对应章节为准重新评审，不直接采用报告原文的优先级。

**剩余风险按我排的优先级**：

1. **语义对账仍是空座**：`SemanticReconciler` 只有 trait 与 mock，「AI 提议 + 人确认」这条核心叙事尚未接真实 LLM。这是差异化叙事与实现之间目前最大的缺口。
2. **证据门未跑**：漂移报告能否让看板重新被信任、round-trip 无损率基线，都要等 2 周 dogfooding 与外部试用数据。在此之前不应扩功能面。
3. **分发与商业化未动**：`.app` 仅 ad-hoc 签名；对账引擎是否开源、买断还是 Obsidian 模型（`DECISIONS.md` 决策②③）尚未拍板。竞品窗口期（Backlog.md 周更活跃）在流逝。
4. **已记录的小缺口**：`TODO.md` 待办中列明——hooks context 跨平台进程终止、Playwright 回归进 CI、release 构建、research 文档中的本机绝对路径清理等。均已被工具自身追踪，属健康状态。

**一个元观察**：从调研（08-30）到通过独立验证、能自举管理自身开发的 MVP（08-31）只用了两天，且验证过程严格到「用注入缺陷检验测试、如实记录验证方自身的 6 次错误」。这个速度与质量的组合本身就是产品命题的论证——AI 时代开发瓶颈不在写码，而在任务真相的维护与核对；本仓库正在用自己的工具解决自己的这个问题。
