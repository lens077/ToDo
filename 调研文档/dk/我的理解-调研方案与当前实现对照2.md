## 3. `1.md` 的主张还原

### 3.1 痛点与定位

AI Coding Agent 高频修改代码但不回写任务状态，产生「TODO 漂移」，任务看板沦为无人维护的信息孤岛。产品定位：面向 AI 时代、高性能、本地优先、支持多端与 cURL 访问、具备 AI 强同步能力的开发者 Todo 工具。

### 3.2 技术方案

- 技术栈：Tauri v2（Rust 后端）+ SQLite（WAL 模式）+ Axum 嵌入式服务 + Vite + Solid.js。
- 数据模式：本地 Markdown 为主、SQLite 为辅；`TODO.md` 是提交至 Git 的唯一事实标准。
- 解析：pulldown-cmark 事件流增量解析，宣称万行文件加载与修改响应 10 ms 以内；提及参考 `/Users/sumery/lens077/cat` 的实现机制。
- AI 接入：原生 MCP Server（Stdio 与 SSE 传输）+ Agent Skills。Skill 指令要求 agent 在完成后「必须调用 `todo_update` 标记 done」，生成 commit 前「强制调用 `todo_sync_reality` 校验」。
- 扩展能力：多 Git 仓库导入（git2-rs）、代码注释扫描（ignore crate + 正则提取 `// TODO:`、`/* FIXME: */`）、REST API 与 cURL 操作、ntfy 推送与 Webhook。
- 性能目标：文中同时出现「冷启动小于 1 秒」（定位表述）与「用户要求 2 秒以内」（架构章节），并引用 Tauri 冷启动 0.3–0.8 s、内存约 50 MB。

### 3.3 市场判断与商业化

- 竞品对照对象：Linear、Monday.com、TASKS.md 生态、clt-rs、pi-task-manager、开源 MCP Todo Server。结论是「市场不存在完全雷同的产品」。
- 商业化：Open-Core 三档——Community 开源免费；Pro 闭源增值，$6/月或 $59/年；Team $15/席位/月或私有化买断。
- 路线图：第 1–4 周内核与 AST 解析；第 5–8 周 MCP Server 与强同步；第 9–12 周 Axum REST、多源扫描与通知。

## 4. 当前实现的现状

### 4.1 总体结构

Cargo workspace 三成员：`crates/todo-core`（解析、保真回写、文件锁、SQLite 投影、对账、桌面后端）、`crates/todo-cli`（canonical CLI，二进制名 `todo`）、`apps/desktop/src-tauri`（Tauri 2 host，直接调用 todo-core）。前端为 React，构建工具 Vite。README 明确：v1 不包含 MCP、账号、云同步和团队空间。

### 4.2 格式规范（`docs/format-spec-v1.md`）

- 文件身份：frontmatter `todo-spec: 1` 必需；`columns` 定义列的稳定 id 与显示名，`type: done` 列自动完成。
- 任务行：GFM checkbox + 正文 + 稳定 ID `<!--t:xxx-->`（随机 base36，至少 6 位，冲突加长）+ 行尾元数据 token：`#标签`、`@负责人`、`📅截止`、`✅完成日`、`!1`–`!4` 优先级、`^整数` 排序、`🔗sha..sha` 物证、`⛔id` 依赖、`→路径#id` 引用。
- 兼容与安全：未知 token 原样保留；非标准 checkbox（如 `[-]`）不解析为任务，但必须记录并由 lint 警告（「静默不可见比不支持更危险」）；代码围栏与行内代码排除；检测到 Git 冲突标记即拒绝解析、进入只读。
- 预留：`→todos/<分类>.md#id` 溢出语法写进 v1 但 MVP 不实现（决策 D8：方案 A 起步、分类拆分兜底）。

### 4.3 回写引擎（`crates/todo-core/src/write.rs`、`lock.rs`）

- 只做字节区间外科手术：pulldown-cmark `OffsetIter` 取任务行区间后按区间替换，任何情况下不从 AST 重新序列化整个文件。
- 未触碰行逐字节不变，覆盖 CRLF/LF、BOM、缩进与行尾空白。
- 并发防护三层组合：advisory lock（`.<文件名>.lock` + flock，读取在锁内进行）、乐观锁（mtime + 内容 hash）、原子写（临时文件 + rename）。
- 写前校验编辑区间不重叠，写盘前逐段比对所有保留区必须逐字节相同，写后重新解析输出确认仍是合法 v1 文件。

### 4.4 对账引擎（`crates/todo-core/src/reconcile.rs`，规范 §6.5）

- 结构层：重复 ID、死引用、孤儿依赖、非标准 checkbox；定位为零误报。
- Git 物证层：校验 `🔗from..to` 的 commit 是否存在、是否被 revert，提取 changed files 作为语义层候选。浅克隆或 partial clone 时跳过并明示。
- 语义层：`SemanticReconciler` trait 已定义，当前仅有 `MockSemanticReconciler`，真实 LLM 判定尚未接入。
- 安全底线写进规范：`🔗` 与 `⛔` token 在任何情况下不删除；完成状态只升不降，完成判定一律 `suspected`；`--apply` 仅执行一种自动修复——无外部引用的重复 ID 重生成；apply 后必须报告「已应用 N 项、跳过 M 项」。

### 4.5 CLI 与 agent 接入（`crates/todo-cli`）

- 命令面：`init [--adopt]`、`list`、`add`、`done`/`undone`、`evidence <id> --from <sha> [--to <sha>]`、`next`、`lint`、`reconcile [--apply] [--no-semantic]`、`hooks preview|install|uninstall|instructions`。
- 机器可读：`--json` 输出 `schema`/`ok`/`data` 三段式 envelope，schema 带版本号；退出码 0–6 各有定义。
- agent 接入走 CLI + hooks，不走 MCP（决策 D1）：`hooks install` 向 `~/.claude/settings.json` 写入 SessionStart hook，会话开始时注入 `todo next` 与结构层对账摘要（上限 40 行）；`hooks instructions` 向 `CLAUDE.md`/`AGENTS.md` 写入托管指令块，约定「开工记录起始 commit → 提交后 `todo evidence` → `todo done` → 交接前跑 `reconcile --no-semantic`」。Codex 无 SessionStart 机制，仅提供指令块。

### 4.6 桌面端（`apps/desktop`）

- 三个一级视图：看板（新增、完成、跨列拖动）、今日（逾期/今天/未来 7 天，纯派生不拥有数据）、随记（Capture 收件箱与分拣）。
- 架构：Tauri host 直接链接 todo-core，不 spawn CLI 子进程（ADR 0001）；命令体集中在 `ops::DesktopOps`，`#[tauri::command]` 为薄适配层。
- 同步：notify 文件 watcher（100 ms debounce）推送新 Snapshot；Snapshot 带 revision，前端丢弃迟到事件；解析失败、冲突标记、锁超时进入明确的只读或重试状态。
- Capture：个人全局收件箱 `~/.todo/inbox.md`，自定义带字节长度的记录格式，单条上限 64 KB；不属于任何项目、没有完成状态，经 Triage 才转化为项目任务。全局快捷键 macOS `Cmd+Shift+Space`、其他平台 `Ctrl+Shift+Space`，速记窗口预创建。

### 4.7 SQLite 投影（`crates/todo-core/src/projection.rs`）

已实现全量重建与按文件增量更新，带 schema hash 自动重建。经验证「无任何反向写文件路径」，不构成第二事实源。当前未接入 `list` 与桌面主链路：实测 1000 任务 `list` 约 31 ms 而全量投影重建约 9 ms，瓶颈在进程启动而非解析；接入触发条件记录为任务量约 10000 或出现常驻进程。

### 4.8 质量与实测数字（`docs/verification-log.md`）

验证方法为「captain 独立验证，不采信实现方自测」。关键实测：

| 项 | 实测结果 | 预算/目标 |
|---|---|---|
| 桌面冷启动（standalone） | 连续 5 次 330.5–370.0 ms | < 2 s（桌面 spec） |
| 桌面冷启动（`.app` bundle） | 首次 1204.9 ms，复核 590.5 ms | < 2 s |
| 速记快捷键 dispatch | 2–4 ms | 唤起感知 < 100 ms |
| 1000 任务投影全量重建 | median 8.99 ms / p95 9.54 ms | < 100 ms |
| 16 进程并发写同一文件 | 全部成功，零丢失更新 | — |

## 5. 对照：一致点与分歧点

### 5.1 一致点

- 痛点判断：TODO 漂移真实存在，需要工具层解决。
- 数据主权：本地优先，仓库内 `TODO.md` 是唯一事实源，SQLite 只是派生。
- 技术底座：Tauri 2 + Rust + SQLite + pulldown-cmark + notify 文件监视。
- 性能取向：冷启动与交互延迟是硬指标。实测冷启动 330 ms–1.2 s，落在 `1.md` 的「小于 1 秒」口径附近、且低于桌面 spec 的 2 秒预算。
- 双向性：看板操作回写 Markdown，外部编辑驱动界面刷新，两条链路均已实现。

### 5.2 分歧点总表

| 议题 | `1.md` 主张 | 当前实现的选择 | 依据 |
|---|---|---|---|
| AI 接入通道 | MCP Server（Stdio + SSE）+ Skills 是核心 | v1 去 MCP，CLI + hooks 是 canonical 接口；`--json` 面留作未来 MCP 薄壳的 schema | 决策 D1；研报引证 CLI > hooks > MCP |
| 「同步事实」语义 | agent 完成后必须自动标记 done；引擎自动纠偏 | 对账只报告不改状态；物证不等于完成；完成判定一律 `suspected`，由人裁决 | 规范 §6.5；研报 e §1 漂移成因 |
| 竞品判断 | 「市场不存在完全雷同产品」；对照 clt-rs、pi-task-manager 等 | 「存在雷同工具，重合度最高的是 Backlog.md（6,573★）」；从 Vibe Kanban（27,953★，2026-04-10 关停）提炼「免登录铁律」 | 研报 a、e；`1.md` 所列 clt-rs、pi-task-manager 未出现在仓库主报告竞品总表中 |
| REST/cURL、ntfy、多仓库、注释扫描 | 第三阶段核心内容（第 9–12 周） | v1 明确不做（桌面 spec §8），排在修订路线第 6–10 位 | `g-decisions-addendum.md` §6、§7.5 |
| 前端框架 | Solid.js（细粒度响应性，规避虚拟 DOM） | React；性能靠 Rust 端派生、预创建窗口与本地权威数据达成，实测在预算内 | 研报 c：「快慢的决定变量是权威数据在本地还是云端，不是框架」 |
| SQLite 角色 | WAL + mmap 高速缓存中介 | 「派生投影，可随时从 Markdown 重建」；实测后主动推迟接入主链路 | 验证日志 T2、T3 缺口 1 裁决 |
| 单文件膨胀 | 未正面处理 | v1 预留 `→todos/<分类>.md#id` 溢出语法与死链校验；决策 A 起步、C 兜底 | `DECISIONS.md` 决策①、D8 |
| 商业化 | Open-Core 订阅：Pro $6/月或 $59/年，Team $15/席位/月 | 按边际成本拆三档：免费（单仓完整、永不强制登录、BYOK）/ 买断（多仓聚合、回顾视图、ntfy）/ 订阅（托管 AI、云中继） | `g-decisions-addendum.md` §5.3 |

### 5.3 最关键的一处分歧：谁有权写完成状态

`1.md` 的 Skill 指令让 agent 在改码后自动把任务标记为 done，并由「同步事实」引擎自动纠偏。当前实现的立场相反：agent 只记录物证（`todo evidence` 绑定 commit 范围），对账引擎核对物证与代码现实后输出报告，完成状态的变更由人确认；证据 token 在任何情况下不被引擎删除。

我认为实现的立场更站得住。仓库研报引证的社区实测（约 27% 幽灵任务、「creates 可靠、completes 有损」）说明「信任 agent 自动写完成状态」正是漂移的成因而不是解法；`1.md` 在这一点上是在用引发问题的机制去解决问题。「物证 + 对账 + 人确认」同时也是研报确认的全类目真空，是当前方案最硬的差异化。

### 5.4 顺带修正 `1.md` 的两处口径

- 性能口径不一致：定位段写「冷启动小于 1 秒」，架构段写「用户要求 2 秒以内」。仓库以桌面 spec 的 2 秒预算为准，实测已达到更严的口径。
- 「毫秒级双向实时 AST 解析与回写」的表述容易误导：当前实现刻意避免「从 AST 回写」，回写走字节区间替换。研报 b 的对照实验（Obsidian Kanban 全文件重序列化毁数据弃坑 vs Obsidian Tasks 行级改写存活）支持这一选择。

## 6. `1.md` 未覆盖、当前实现已解决的问题

- 多 agent 并发与 ID 撞号：随机 base36 稳定 ID + 行级最小 diff + advisory lock + 乐观锁。
- Git 冲突现场：检测到冲突标记即只读降级，不解析、不崩溃。
- 个人随记与项目任务的分层：Capture 存全局 `~/.todo/inbox.md`，经 Triage 才进项目仓库，避免随想污染 Git 历史。
- 手写文件的接管路径：`todo init --adopt` 显式接管普通 GFM 清单并补齐 ID，不自动改写。
- agent 生态的「不被忽略」问题：SessionStart hook 主动注入任务快照与对账摘要，而不是等 agent 记得调用工具。

与 `TODO.md` 的未完成任务一致，任务清单是诚实的：

- 语义对账仍是 Mock，BYOK LLM 判定未接入（trait 缝已留好）。
- `DECISIONS.md` 提到的 `todo archive` 归档命令尚未实现。
- SQLite 投影未接入主链路（有意推迟，触发条件已记录）。
- 三项桌面人工验收未完成（原生文件选择器、看板写回、外部编辑刷新）；前端 Playwright 回归未纳入 CI。
- 无 release 构建与分发；hooks 自动注入目前只覆盖 Claude，Codex 走指令块，Cursor/Windsurf 未覆盖。
- `1.md` 与原始需求中的 REST/cURL、ntfy、多仓库、注释扫描、移动端：均在修订路线的后位（第 6 位之后），未开工。

## 8. 对 `1.md` 的使用建议

1. 不据其调整已拍板决策：MCP 后置、对账只报告不改写、CLI canonical、A 方案存储——这些决策的证据链比 `1.md` 深。
2. 吸收其需求清单价值：REST/cURL、ntfy、多视图（四象限、甘特）是真实诉求，按 `g-decisions-addendum.md` §7.5 的既定位次推进即可。
3. 竞品部分不采信：以仓库 `research/a`、`research/README.md` 的竞品总表为准。
4. 若后续要接 MCP：按 D1 预留的路径，用 rmcp 给 CLI `--json` 面套薄壳，不另建第二语义层。
